# 햄버거 매장 운영 MVP — 구현 요구사항

기준일 2026-10-07. `phase0-design.md`의 설계는 사용자가 구현 승인했다. 해당 문서의 과거 ‘아직 구현하지 않는다’ 문구는 승인 전 기록이다. 현재는 전체 MVP 구현·검증을 진행한다.

## 범위와 기본값

첫 매장은 햄버거 메뉴 하나, Owner 한 명과 Staff 한 명으로 시작한다. 공개 회원가입 없이 초대로 계정을 추가한다. 하루 영업 종료 후 Owner가 판매를 합산 입력한다. 한국어 반응형 웹, Asia/Seoul 자정 영업일, 예약 기본 90분과 한 테이블 배정이 기본이다. 실제 가격·레시피를 확정한 것처럼 데모 값을 표시하지 않는다. 운영 중 LLM API를 호출하지 않는다.

Must Have: 인증·매장 분리·초대·역할 변경, 메뉴/재료/레시피, 재고 원장/실사, 일합산 판매/정정/환불/Mock POS, 공급업체/추천 발주/부분 입고, 수동 예약/테이블, 시설/수리/비용, 기타 수입·지출·추정 손익, 통합 대시보드, 모바일 탐색, 백업·분리 복구 검증이다. 실제 POS·은행·외부 예약 API, SaaS 결제, 자동 주문 전송, 유통기한 로트 추적은 후속 범위다.

| --- | --- | --- | --- |

| 재고 사용·폐기, 시설 이상 접수 | 허용 | 허용 | 허용 |

모든 요청에서 현재 활성 계정/StoreMember를 확인한다. 클라이언트 storeId만 신뢰하지 않는다. 타 매장 자원 참조를 조회와 변경 모두 차단한다. Staff 응답에는 매출·원가·지출·수리비를 포함하지 않는다. 마지막 Owner 제거는 막는다.

인증은 비밀번호 해시, 서명·만료 세션, HttpOnly/SameSite 쿠키, 운영 HTTPS Secure, 로그인 실패 제한, 변경 요청 Origin/CSRF 검사, 해시 저장·만료·한 번만 사용 가능한 초대가 필수다. 인증 키와 DB 접속 값은 로컬 비밀 파일 또는 환경 설정으로 주입하고 Git/문서/로그에 넣지 않는다.

## 데이터·계산 불변식

- 재고 변경은 append-only 원장을 남기고 원장+잔고를 한 트랜잭션에서 처리한다. 실사는 현재 잔고와 차이를 기록한다. 입력 단위/수량/사유를 검증한다. 판매 시 부족재고는 음수 및 경고로 남긴다.
- 레시피는 새 버전을 만들며 과거 버전을 수정하지 않는다. 판매는 당시 사용한 레시피를 스냅샷으로 저장하고 정정 시 그 스냅샷을 사용한다.
- 하루 동일 레시피 운영을 보장하기 위해 최초 레시피는 즉시 적용하고 이후 버전은 다음 한국시간 자정부터 적용한다. 판매/Mock POS는 해당 영업일 다음 자정 이전에 유효한 버전만 선택한다. 새 버전 적용시각을 화면에 표시한다. 메뉴 가격은 하루 합산에서 사용자가 실제 적용 단가를 명시하며 영업 도중 변경하지 않도록 안내한다.
- 매장/영업일/메뉴당 일합산 한 건. 사건별 idempotency key와 내용 검사를 적용한다. 같은 키+다른 내용은 409다. 정정은 revision 충돌 검사 후 차이만 원장에 반영한다.
- 판매수량은 조리한 수량이다. 조리 후 환불은 매출만 감소하며 재료를 자동 복원하지 않는다. 오입력 수량 감소 정정은 과차감분을 복원한다. 환불 누계는 실제 순매출 상한을 넘지 않는다.
- 영업일과 기록시각을 구분한다. 일합산은 지정 영업일 매출이다. 전월 판매를 당월 환불하면 환불은 당월 음수 매출이다. 실사 이후 그 실사에 포함된 과거 판매 추가/수량 변경은 자동 반영을 차단하고 재대사를 안내한다.
- 미입력 판매와 확정된 판매 0건은 다르다. 대시보드는 마지막 판매 반영일 및 재고가 기록 기준임을 표시한다.
- 발주 부족 기준은 현재 재고 ≤ 최소. 추천 = ceil(max(0, 목표−현재−미입고량)/묶음)×묶음. 미입고량은 확정/부분입고 발주만 포함한다. 초안/취소는 제외한다. 발주 확정 후 품목 임의 변경, 초과 입고, 중복 입고를 차단한다. 입고와 실제 비용 지급은 별개다.
- 예약은 활성 상태의 동일 테이블 `[시작, 종료)` 겹침과 정원 초과를 차단한다. 종료=다음 시작은 허용하고 취소/노쇼는 자리를 해제한다. 동시에 들어온 요청도 행 잠금 또는 DB 제약으로 보호한다.
- 수리 완료·이력·비용은 원자적으로 처리하고 source 고유키로 한 번만 비용 반영한다. 비용 조회 불가 역할에는 이력에서도 금액을 지운다.
- KRW 금액은 원 단위 정수, 재료 수량은 정확한 소수 계산이다. 판매 매출을 수동 수입에 중복 생성하지 않는다. 추정 운영손익=판매 사건 순매출+영업 기타수입−기록 운영지출. 자금투입/대출/이체는 손익 제외다. 실제 은행잔액·회계이익이라고 표시하지 않는다.

## 완료 증거

| ID | 실행하여 확인할 조건 |
| --- | --- |
| AUTH | Owner/Staff 로그인·초대·로그아웃, 초대 재사용/만료 차단, Staff 금융 403, 멤버 비활성화 즉시 접근 차단, 두 매장 교차 조회/변경 실패 |
| INV | 2000g 입고−300g 사용−100g 폐기=1600g, 1500g 실사 시 −100g 원장, 잔고=원장합계, 단위/음수 입력 차단 |
| SALE | 번/패티 각100→하루20판매→각80, 재시도 그대로80, 25정정→각75, 정정 재시도 그대로75, 조리환불 재고 그대로75 |
| HIST | 과거 영업일 귀속, 미입력/0건 구별, 실사 후 과거 수량 변경 차단, 새 레시피가 과거 정정 소비를 변경하지 않음 |
| PO | 현재18/최소20/목표60/묶음20→60 추천; 미입고40→20 추천; 발주100 입고40→부분, +60→완료, 중복/초과 입고 차단 |
| RES | 수동 전화/네이버/캐치테이블 저장, 중복 시간과 동시 충돌 차단, 끝=시작 허용, 정원 초과 차단, 취소 후 재배정, 타 매장 테이블 차단 |
| FIX | Staff 이상 접수→Owner 수리완료 50000원 비용 한 건, 재요청 비용 중복 없음, Staff 금액 비노출 |
| FIN | 10×10000−할인5000−환불10000=85000 매출, 비용50000→추정손익35000, 판매수입 중복없음, 서울 자정/전월 환불 귀속 |
| WEB | 실제 브라우저 로그인→판매→재고→추천/발주/입고→예약→수리비→대시보드; 360px 핵심 업무 가능; 타입 검사/빌드/테스트 모두 실제 완료 |
| OPS | 빈 DB 마이그레이션, 데모 seed, 백업 분리 DB 복구 후 원장/잔고/예약 비교, 재현 설치/시작 절차 저장 |

테스트 0건·열린 포트·파일만 존재하는 경우는 증거가 아니다. 예상 실패/skip/미실행을 통과와 구분한다. 검증한 범위 밖의 무결함을 주장하지 않는다. 실매장 파일럿과 실제 개인정보 안내 확인은 소프트웨어 자동검증과 구분하여 보고한다.

| 개발 DB와 키 | `/workspace/.local/practice/runtime.env`에서 로컬 읽기. 저장소에는 값 없이 예시 변수명만 둔다 |
| 팀 파일 소유 | 구현자 app/Prisma, 테스터 tests/test-plan, 설계자 design/operations, 요구사항 담당 requirements |

최종 acceptance와 수정 기록은 `decisions-and-defects.md`를 따른다. 재현 설치 이후 Vitest7/7, Playwright19/19(API18 + 실제 브라우저 흐름1), 타입 검사 및 production build가 통과했다. production Owner8개 화면·모바일·Owner/Staff 로그인·Staff 금액 접근 차단, 백업 별도 복구 및 전체 행 digest 비교를 실행했다. 실제 매장 파일럿·외부 POS·공개 HTTPS 배포·새 cloud task 복원까지 검증했다고 주장하지 않는다.

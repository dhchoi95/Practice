# 하루사주 구현물 독립 검토 보고서

검토일: 2026-10-20. 대상: 사용자가 첨부한 `saju-review-package.zip`과 `saju-review-screens.pdf`.

## 1. 판정

**공개 전 수정 필요.** 핵심 입력·계산·페이지 연결은 실제로 실행되며, 이번에 실행한 경로에서 출생정보의 서버 전송이나 확정적인 핵심 계산 오류는 발견하지 않았다. 그러나 일간 미확정 상태의 본문 모순과 원고의 실질적 다양성 부족은 원래 요구사항에 비추어 공개 전에 수정해야 한다.

이는 사주의 미래 예측 능력에 관한 인증이나 명리 전문가 검수 판정이 아니다. 선택한 계산 정책·소프트웨어 동작·콘텐츠·개인정보·화면을 검토한 결과다.

- **P0 확정 발견: 0건.** 조사한 범위에서 핵심 경로 중단·출생정보 유출·명백한 기둥 계산 오류를 확정하지 못했다는 뜻이며, 결함이 전혀 없다는 뜻은 아니다.
- **P1: 2건.** 일간 미확정 시 설명 모순, 오행 보완 원고의 주제별 실질적 중복.
- **P2: 4건.** 한국어 조사 오류, 연간 구간의 연도 누락, 닫힌 상세 영역의 인쇄 누락, 별자리 선택 기준의 작은 글씨.
- 추가 검증 발견: ICU Dangi와 30일 불일치를 발견했으나 한국천문연구원 대조 결과 **앱이 맞는 사례**였다. 앱의 달력 오류로 분류하지 않는다.

지금은 검토만 수행했다. 원본 앱 소스·콘텐츠·문서를 수정하지 않았고, 공개 배포·계정 변경·유료 서비스 실행을 하지 않았다. 의존성 설치, 검증용 별도 스크립트 작성, 로컬 정적 서버 실행, 빌드와 테스트 산출물 생성만 수행했다.

## 2. 검토 기준과 자료의 신뢰 범위

검토 순서는 `REVIEW_REQUEST.md` → `START_HERE.md` → `requirements/original-execution-prompt.md` → README·계산 정책·구조·제한 → 소스·테스트·원고 → 화면·기존 증거였다.

ZIP의 원래 프롬프트는 앞서 전달된 프롬프트와 내용이 동일한 것을 바이트 비교로 확인했다. ZIP manifest의 해시를 확인한 원래 소스·문서·증거 파일 100개에서는 불일치가 없었다. 정적 `out/`는 재빌드 대상이므로 소스 불변성 확인과 구분했다. manifest 자체는 정확성 인증으로 취급하지 않았다.

기존 완료 체크리스트, 184개 테스트·43개 E2E 보고, Lighthouse 100점은 **제공자가 작성한 증거**로만 읽었다. 아래의 직접 실행 결과와 구분한다.

심각도는 이번 검토 요청에 맞춰 사용했다.

| 등급 | 의미 |
|---|---|
| P0 | 잘못된 핵심 계산, 개인정보 유출, 핵심 경로 중단 |
| P1 | 중요한 기능·콘텐츠 요구사항·접근성·검증 문제 |
| P2 | 영향이 제한된 표시·문장·운영 개선 |

이 보고서의 `project/...` 경로와 줄 번호는 **첨부 ZIP 내부의 원본 파일 기준**이다. 수정 후에는 줄 번호가 달라질 수 있다.

## 3. 중요한 발견부터

### F-01 · P1 · 일간 미확정인데 본문은 ‘확정한 일간’을 전제로 설명한다

**분류:** 확정된 콘텐츠 적용 오류. **확신도:** 높음. 계산 엔진이 일간을 잘못 만들어낸 오류와는 구분한다.

**근거 파일**

- `project/src/content/rules.json:6764`의 `unknown-personality`. `requires`에는 `natal.hourKnown`만 있고 `natal.dayStem`은 없다.
- 같은 파일 `:6912`의 `unknown-single`도 ‘알려진 일간’을 전제로 한다.
- 같은 파일 `:6727`의 `unknown-general` 역시 확정된 일간을 이용한다는 표현을 사용한다.
- `project/src/domain/interpretation/engine.ts:19-35`: requires를 만족하면 규칙을 선택한다.
- 같은 파일 `:58-63`: 일간 미확정은 제목·제한 문구에 표시하지만 이미 선택된 본문을 제거하지 않는다.
- `project/tests/integration/interpretation.test.ts:101` 이후의 DST 제한 사례는 제한 문구 유무만 검사하므로 본문의 전제 모순을 놓친다.

**재현**

1. `/fortune/personality/`에 진입한다.
2. 양력 `1987-06-01`, 한국 출생, **시간 모름**을 선택한다.
3. 결과를 읽는다. 같은 입력으로 솔로사주도 확인할 수 있다.

**예상**

서머타임 시계의 하루가 한국 표준시의 전날·당일에 걸치므로 일간을 확정할 수 없다는 정책에 맞게, 일간에 의존하지 않는 안내만 제공해야 한다.

**실제 직접 확인**

- 계산 결과: `day: null`, `hour: null`, `dayMaster: null`.
- 결과 제목: ‘일간이 미확정이라 기본 성향 풀이는 제한해요’.
- 제한 안내: ‘일간에 의존하는 문장은 제외했어요’.
- 그런데 본문에는 **‘시간 미상 성격 풀이는 확정한 일간의 상징을 중심으로 읽어요’**가 표시된다.

즉, 제한 안내와 실제 선택한 원고가 모순된다. 브라우저와 도메인 함수 양쪽에서 재현했다.

**영향**

시간 미상 사용자가 불확실성을 정확하게 이해하기 어렵다. 특히 1987·1988년 서머타임 기간의 시간 미상 입력에서 나타날 수 있다. 제한 상태를 표시했다는 이유만으로 해당 기능이 완전하다고 볼 수 없다.

**수정 방향**

- ‘시간만 모름, 일간은 확정’과 ‘일간도 미확정’을 원고 조건에서 분리한다.
- 일간을 전제하는 문장은 `requires`에 `natal.dayStem`을 추가한다.
- 일간 미확정 전용 중립 안내를 별도로 작성한다.
- 기본 성향·솔로·종합 등 모든 관련 메뉴에서 미확정 상태의 본문에 ‘확정한 일간’·일간별 성향 문장이 나오지 않는 회귀 검사를 추가한다.
- 기둥 계산을 임의 시각으로 바꿔 일간을 채우는 방법으로 해결하지 않는다.

### F-02 · P1 · 오행 보완 35개는 주제 단어를 바꾼 5종 원고에 가깝다

**분류:** 원래 콘텐츠 다양성 요구의 부분 미충족. **확신도:** 높음. 전체 180개가 전부 중복이라는 뜻은 아니다.

**근거 파일**

- `project/src/content/rules.json:2803`부터의 `element-0-general` 등 오행 보완 35개.
- 예: `:2841`의 `element-0-personality`와 동일 오행의 나머지 6주제.
- `project/scripts/content-tools.ts:20` 이후: 중복 검사가 완전히 동일한 문자열만 탐지한다.
- `project/tests/integration/interpretation.test.ts:59` 이후: 레코드 개수와 완전 중복 여부를 검사한다.
- 원래 요구사항 15절은 숫자뿐 아니라 ‘유효하고 중복되지 않는 원고’, 주제별 실제 내용 차이를 요구한다.

**재현과 직접 확인**

1. 35개 `element-*` 레코드를 추출한다.
2. 같은 오행의 7주제를 비교한다.
3. 첫 문단의 ‘나의 생활 전체’, ‘반복되는 나의 습관’ 등 주제 문자열을 같은 `{topic}`으로 치환한다.
4. 두 본문 문단을 비교한다.

검사 결과, **각 오행마다 7개 본문이 같은 1개 본문으로 합쳐졌다. 총 35개가 5개 템플릿으로 정규화된다.** 조건 역시 각 오행의 단순 개수 `>= 2`로 같다.

예를 들어 목의 종합/성격 원고는 주제 명칭만 바뀌고 ‘계획을 처음 세웠을 때와 유지할 때 필요한 자원이 다를 수 있다’는 내용은 같다. 연애·직업·대인관계에 맞춘 상황이나 행동 차이가 충분하지 않다.

**예상**

재사용하는 공통 설명은 공통 설명으로 관리하고, 독립 원고 수에는 주제별로 다른 해석 역할과 구체적인 조언이 있는 항목을 세어야 한다.

**실제와 한계**

JSON 180개·스키마·완전 중복 검사 통과는 사실이다. 70개 일간×주제 기본 원고에는 실제로 다른 문장도 있다. 하지만 35개 보완 원고를 35개의 실질적으로 구별된 설명으로 볼 근거는 부족하다. 따라서 ‘콘텐츠 수와 실질적 다양성을 모두 충족’으로 완료 처리한 부분은 재검토해야 한다.

**수정 방향**

- 공통 오행 설명 5개는 재사용 모듈로 분리한다.
- 주제별 보완에는 서로 다른 상황·관찰 포인트·행동 제안을 작성한다.
- 검증 가능한 복합 조건을 추가할 경우 그 조건의 계산·해석 근거도 함께 정의한다. 숫자를 채우려고 임의의 명리 규칙을 만들지 않는다.
- 중복 lint에는 주제명 치환 후 비교 등 템플릿 중복 탐지를 추가한다.
- 고유 원고 수, 공통 모듈 수, 주제 coverage를 별도 보고한다. 전문가 검토 미완료 표시는 유지한다.

**영향**

**수정 방향**

저장 문장을 직접 교정하거나 받침에 맞는 조사 처리 함수를 사용한다. 일부 예시만 고치지 말고 전체 원고·조언·기간 변형을 확인한다. 자동 검사와 사람이 읽는 교정은 별도로 수행한다.

### F-05 · P2 · 닫힌 상세 영역은 인쇄 CSS만으로 펼쳐지지 않는다

**분류:** 확정된 인쇄 동작 문제. **확신도:** 높음.

**근거 파일**

- `project/src/styles/globals.css:10`의 `@media print`: `.disclosure-body{display:block!important}`와 summary 숨김.
- `project/src/components/CalculationDetails.tsx:8` 이후: 계산 기준과 입력 날짜·사주표가 닫힌 `details` 안에 있다.
- `project/tests/e2e/site.spec.ts`의 인쇄 테스트는 버튼 호출과 본문 표시만 검사한다.

**재현**

1. 양력 `1992-05-15 10:30`으로 종합 결과를 연다.
2. ‘내 사주표와 오행 살펴보기’를 **열지 않은 상태**로 인쇄한다.
3. 인쇄 미디어에서 해당 body의 실제 표시 영역과 출력 PDF를 확인한다.

**실제 직접 확인**

body의 computed `display`는 block이지만 `checkVisibility()`는 false이고 실제 크기는 0×0이다. 출력 PDF에도 닫힌 상세 안의 표준시 계산 기준·사주표가 포함되지 않는다. 브라우저의 닫힌 details 처리 때문에 자식의 display만 바꿔서는 해결되지 않는다.

**예상 / 영향**

인쇄할 결과에는 적어도 적용 기준 안내가 안정적으로 남아야 한다. 이용자가 먼저 상세를 펼쳤는지에 따라 기준·표의 포함 여부가 달라지는 동작은 명확히 정리해야 한다. 주요 풀이 본문 자체가 인쇄되지 않는 문제는 아니다.

**수정 방향**

- 인쇄 전 details 상태를 저장하고 필요한 항목을 연 뒤 인쇄 후 복원하거나,
- 기준 요약·인쇄용 정보를 details 밖의 별도 인쇄 영역에 제공한다.
- ‘열지 않은 상태’와 ‘열린 상태’를 각각 PDF 내용으로 검증한다.

### F-06 · P2 · 별자리 선택에 필요한 날짜 범위가 모바일에서 10px다

**분류:** 확정된 UI 수치와 가독성 개선점. **확신도:** 높음. 이것만으로 WCAG 전체 실패라고 단정하지 않는다.

**근거 파일**

- `project/src/styles/globals.css:7`의 모바일 `.light-choice small{font-size:10px}`.
- `project/src/components/FortuneEntry.tsx`의 별자리 날짜 범위 표시.
- 원래 요구사항의 주요 보조 설명 14~15px 지향, 40~60대 가독성 고려.

**재현**

390px 화면에서 `/fortune/constellation/`을 열고 별자리 아래 날짜 범위를 확인한다. 브라우저 computed font-size가 **10px**였다.

**예상 / 영향**

별자리 이름을 모르는 사람이 자신에게 맞는 유형을 고르는 기준이므로, 장식 글씨처럼 작게 처리하지 않는 편이 좋다.

**수정 방향**

날짜 범위를 13~14px 이상으로 조정하고 필요하면 모바일 선택 영역을 2열로 바꾼다. 폼의 전체 클릭 영역·줄바꿈·200% 확대를 함께 확인한다.

## 4. 계산과 정확성 근거: 직접 확인한 내용

### 4.1 달력 변환 전 범위 비교와 ICU 예외

지원 시작일 1962-01-01부터 기준일 2026-10-20까지 **23,669개 양력 날짜**를 매일 순회했다.

- 앱의 양력→한국 음력 변환과 음력→양력 왕복: 순회한 날짜 모두 왕복 일치.
- 별도 구현인 Node/ICU Dangi의 한국 음력 날짜와 비교: 30일 불일치.
- 불일치 범위: **2017-02-26~2017-03-27**.

불일치를 앱 오류로 바로 확정하지 않았다. 한국천문연구원 ‘월별 음양력’의 공개 양력 2017년 2월·3월 표를 직접 조회해 **59개 날짜 행**을 받아 비교했다. 개인의 실제 생년월일은 제출하지 않았고 공개 월력 조회만 했다.

| 사례 | 한국천문연구원 표 | 앱 | 이 실행 환경의 ICU Dangi |
|---|---|---|---|
| 2017-02-26 | 음력 2017-02-01 | 2017-02-01 | 2017-01-30 |
| 2017-03-27 | 음력 2017-02-30 | 2017-02-30 | 2017-02-29 |
| 2017-03-28 | 음력 2017-03-01 | 2017-03-01 | 2017-03-01 |

59개 행은 모두 앱과 일치했고, 그중 위 30일은 ICU와 달랐다. 따라서 **이 30일은 앱 버그로 세지 않는다.** 이 실행 환경의 ICU 결과를 해당 구간의 절대 정답으로 쓰면 오히려 앱을 틀리게 고칠 수 있다.

출처: <https://astro.kasi.re.kr/life/pageView/5>. 공개 폼의 `search_year=2017`, `search_month=02/03`, `search_dp=1`, `search_check=G`로 조회한 반환 표를 확인했다. 중간에 503이 있었지만 재조회에 성공했다.

권고: 이 예외와 한국천문연구원 기대값을 회귀 사례에 추가한다. 기존 29개 ICU fixture는 출처가 다른 구현이라는 의미가 있지만, 모든 날짜에서 정확한 독립 오라클이라는 의미는 아니다. 위 59일을 제외한 모든 지원일을 한국천문연구원과 비교한 것은 아니다.

### 4.2 절입 시각 비교 확대

제공 fixture는 6개 연도×12개 절입=72개다. 별도 스크립트로 **1962~2050년 전체 89개 연도×12절입=1,068개**를 Astronomy Engine 2.1.19 `SearchSunLongitude`와 비교했다.

| 항목 | 이번 직접 비교 결과 |
|---|---|
| 비교 개수 | 1,068 |
| 프로젝트 기준 90초 초과 | 0 |
| 최대 절댓값 차이 | **51.829초** |
| 최대 차이 사례 | 2003년 입춘 |
| 앱 모델 시각 | 2003-02-04T06:05:20.000Z |
| 비교 모델 시각 | 2003-02-04T06:06:11.829Z |

기존 보고의 44.61초는 기존 72개 표본 안의 최댓값이다. 확대 집합에서 최댓값이 커진 것은 그 보고가 거짓이라는 뜻은 아니다.

90초는 프로젝트가 정한 **모델 간 비교 허용치**다. 실제 관측·공인 절입시각과의 초 단위 정확성 보증이 아니다. 분 단위 입력도 절입 경계에 아주 가까우면 다른 모델과 기둥이 달라질 여지가 남는다. 이 차이를 확정적인 앱 계산 오류로 세지 않았다.

출처: 실제 설치된 `astronomy-engine@2.1.19` 소스와 <https://github.com/cosinekitty/astronomy>. 앱의 절기 함수로 기대값을 생성해 비교하지 않았다.

### 4.3 연·월·일·시주와 시간대

직접 읽은 구현과 직접 통과한 테스트에서 다음을 확인했다.

- 한국 음력 변환과 사주 연·월 간지를 분리한다.
- 중국 음력으로 한국 음력 입력을 대신하지 않는다.
- 절기 원자료의 UTC+8 시계를 UTC 순간으로 바꿔 비교한다.
- 연주는 입춘, 월주는 12개 절입 경계를 사용한다.
- 일주는 JDN 식으로 계산하고 표준시 0시에 바뀐다.
- 시주는 해당 표준시 날짜의 일간을 사용한다. 23시에 외부 엔진의 다음 날 일간을 섞지 않는다.
- 1987·1988년 DST는 IANA 왕복으로 검증하고 gap/fold는 임의 선택하지 않는다.
- 시간 미상은 대표 시각을 실제 출생 시각으로 저장하지 않고, 확정할 수 없는 기둥을 null로 둔다.
- 오행은 확정 천간·지지 대표 오행의 단순 개수이며 강약·용신으로 표시하지 않는다.

일진 30개 비교는 앱의 JDN 계산과 다른 함수·테이블을 비교하는 가치가 있다. 다만 비교 패키지가 음력 변환에도 사용되므로 ‘앱의 모든 역법과 완전히 독립된 공인 근거’로 확대하면 안 된다. 제공 문서는 이 한계를 대체로 구분하고 있다.

남는 한계: 모든 분 단위 출생시각, 모든 DST 가능한 시각, 모든 기둥 조합을 외부 공인 만세력과 전수 비교하지 않았다. 간지 계산 정책의 검증과 미래 예측의 검증은 별개다.

## 5. 실제 기능·개인정보·화면 검토

### 5.1 기능과 상태

홈 9개 타일, 13개 메뉴의 직접 진입·새로고침, 입력·오류 수정·실제 계산·결과, 재사용·입력 수정·다른 사람 보기·입력 삭제를 브라우저에서 검사했다. 결과 URL 단독 진입 시 입력 안내가 나오는 것은 메모리 정책에 맞는 정상 동작이다.

일간 미확정 본문 문제(F-01)를 제외하고, 이번 실행에서 주요 경로 중단을 발견하지 않았다. 기본 결과가 이름만 바뀌고 모든 날짜에 고정되는 구현도 아니다. 다만 콘텐츠의 개인화는 준비된 일간·단순 오행·제한된 관계 규칙에 따른 범위이며 정밀 종합 명리 해석으로 과장하면 안 된다.

### 5.2 개인정보

**이번에 직접 실행한 경로에서는 출생정보의 서버 전송을 발견하지 않았다.**

- 소스 검색에서 앱의 외부 요청·추적·Storage 쓰기·콘솔 기록 경로를 찾지 못했다.
- 메모리 공급자에만 입력을 보관한다.
- 출생정보의 URL/query/fragment 포함, 요청 payload, 콘솔, localStorage/sessionStorage를 확인하는 E2E가 통과했다.
- 추가 검증에서도 요청의 개인 입력 흔적이 없었고 localStorage/sessionStorage와 cookie가 비어 있었다.
- JS 비활성화 상태의 Enter 제출도 직접 테스트했다. 서버 렌더링 때 버튼이 disabled이고 meta CSP의 `form-action 'none'`이 있다.
- 공유는 개인 결과가 아닌 일반 메뉴 링크다. Web Share의 성공·취소와 복사 대안은 모의 API로 검사했다.
- 새로고침, 삭제, 다른 사람 보기가 메모리 정책과 일치한다.

이 결과는 공개 호스팅 전체의 로그 정책 인증이 아니다. 브라우저·확장 기능·OS의 기록까지 영구 삭제한다는 주장도 하지 않는다.

### 5.3 화면과 가독성

첨부 PDF 22쪽을 렌더링해 전체 흐름을 확인했고, 그 안의 375/390px 홈·입력·결과와 1440px 화면을 원본 캡처와 대조했다. 새 로컬 실행에서도 홈·입력·결과와 추가 경계 사례를 확인했다.

상단 한글 분류, 4×2 바로가기, 3×3 타일, 올해 배너가 실제로 구현되어 있다. 과한 원색·흐린 이미지·유리 카드·거대한 SaaS 히어로로 바뀌지 않았다. 결과 본문 17px, 한글 중심 설명과 접힌 계산표는 원래 방향에 맞는다. F-06처럼 일부 선택 기준의 작은 글씨는 개선이 필요하다.

320~1440px 가로 넘침, 메뉴 포커스·ESC·복귀, 키보드, axe 자동 검사, 확대 대응 테스트를 직접 실행했다. 스크롤 넘침이 없다는 사실만으로 모든 화면이 읽기 좋다는 뜻은 아니다. 자동 접근성 테스트도 사람·스크린리더·실기기 검사를 전부 대체하지 않는다.

## 부록. 코드 변경 없이 빠르게 재현하는 방법

프로젝트 디렉터리에서 아래 명령을 실행할 수 있다. 이 명령은 합성 입력으로 함수 결과를 출력하며 앱 파일을 수정하지 않는다. `tsx`의 CLI 파이프 오류가 있는 환경에서도 `node --import tsx` 경로를 사용한다.

```bash
node --import tsx --input-type=module - <<'JS'
import {calculateSaju} from './src/domain/saju/calculate.ts';
import {interpret} from './src/domain/interpretation/engine.ts';
import {targetPeriod} from './src/domain/fortune/period.ts';
const clock={now:()=>new Date('2026-10-20T03:00:00Z')};
const result=calculateSaju({
  calendar:'solar',leap:false,year:1987,month:6,day:1,
  unknownTime:true,nickname:''
},clock);
const reading=interpret('saju','personality',result.features);
console.log('dayMaster:',result.dayMaster);
console.log('headline:',reading.headline);
console.log(reading.sections.flatMap(s=>s.paragraphs).join('\n'));
console.log('year labels:',targetPeriod('year',7,clock).segments.map(s=>s.label));
JS
```

현재 스냅샷에서는 dayMaster가 null인데도 ‘확정한 일간의 상징’이라는 문장이 출력되고, 마지막 연간 label에는 다음 해 연도가 빠진다.

오행35개 템플릿 중복은 다음으로 확인할 수 있다.

```bash
python3 - <<'PY'
import json,re,collections
rules=json.load(open('src/content/rules.json'))
groups=collections.defaultdict(set)
for r in rules:
    if not r['id'].startswith('element-'):
        continue
    topic=re.search(r'집계되어 (.*?)에 관한 보완 설명',r['paragraphs'][0]).group(1)
    groups[r['conditions']['feature']].add(tuple(p.replace(topic,'{topic}') for p in r['paragraphs']))
print({feature:len(texts) for feature,texts in groups.items()})
PY
```

현재 결과는 목·화·토·금·수 각각1개다. 이 결과는 모든 원고가 같은 텍스트라는 의미가 아니라, 주제별 오행 보완35개의 본문이 주제 단어를 제외하면5종이라는 의미다.

# 하루사주 콘텐츠 1.1.0 → 다음 버전 고도화 실행 프롬프트

아래 전체를 Codex에 전달한다. 현재 프로젝트 소스와 `content-review-package.zip`, 개선 문서, 독립 검토 보고서를 함께 제공한다. 경로가 다르면 실제 저장소를 찾고 작업하되 과거 절대 경로를 그대로 가정하지 않는다.

--- 실행 지시 시작 ---

너는 기존 하루사주 사이트의 콘텐츠·규칙·근거·평가 체계를 개선하는 개발자다. 계획만 제시하지 말고 아래 범위의 구현과 검증까지 완료하라. 현재 작업은 코드와 콘텐츠의 고도화이며, 외부 배포·도메인 구입·원격 push·외부 메시지 전송·유료 서비스 가입·모델 학습 서비스 호출은 하지 않는다.

## 목표와 범위

현재 콘텐츠 1.1.0은 조건 원고 210개, 별도 공통 오행 설명 5개, 내부 근거 정의 25개다. 이 숫자를 무조건 늘리지 말라. 첫 목표는 실제로 보이는 한국어 오류와 기간 해석의 추적 오류를 고치는 것이다. 이어 계산 사실·해석·생활 제안을 구분하고, 실행 가능한 반례와 조립 결과 평가를 추가하며, 기존 feature만 사용하는 소규모 복합 조건을 검토 가능한 상태로 준비하라.

서비스 실행 중 OpenAI·Claude·기타 LLM API를 호출하지 않는다. AI는 이 개발 세션의 분석·집필 보조에만 쓴다. 결과는 버전이 있는 정적 콘텐츠와 결정적 코드로 생성한다. 현재 규모 때문에 서버 DB·벡터 DB·로그인·관리자 서버·RAG·파인튜닝을 새로 도입하지 않는다.

독립 검토자는 현재 앱 소스를 고치지 않았다. 보고서의 문제를 실제로 재현한 뒤 고쳐라. 기존 1.0.x 문서 속 과거 구현 지시는 현재 상태를 비교하는 자료다. 작업 시작 시 현재 버전·변경 상태·실제 실행 가능 여부를 확인하라. 사용자 입력이나 기존 미커밋 작업을 덮어쓰지 않는다.

## 1단계 — 기준 상태 고정과 실패 재현

1. 변경 전 원고·근거·스키마·평가 fixture의 해시와 버전을 기록한다. 기존 실행 결과를 읽은 것과 직접 실행한 결과를 구분한다.
2. 현재 230개 단위/통합, 57개 브라우저, 23개 편집 수용 사례, 실제 PDF 9개라는 기준을 확인하되 실제 개수는 저장소 기준으로 다시 센다. 새 테스트를 추가하면 증가분을 구분한다.
3. 평가 기준을 약하게 바꾸어 통과시키지 않는다. 실제 실패한 입력을 고정한 후 수정한다.
4. 각 수정은 `content-review/issues.json`에 외부 지적 ID·재현 입력·대상 원고·수정 버전·검사 연결·상태를 남긴다. 독립 검토가 끝나지 않았으면 `implemented-pending-independent-review` 상태로 둔다.

## 2단계 — CR-01 한국어 오류와 검사 누락 수정

현재 확인된 실패는 다음과 같다.

- `period-{day|month|year}-{1|4|5}`의 `evidence.rationale`에 겁재을·편재을·정재을이 총 9개 있다.
- `knowledge.ts`의 동적 설명은 고정 ‘이에요’를 붙여 병화이에요·무토이에요·임수이에요, 편재이에요 같은 문장을 생성한다.
- `interpretation-bases.json`에는 무은·기은·계은·겁재은·편재은·정재은이 있다. 현재 fact 문자열이 화면에 그대로 쓰이는지부터 구분하되 기준 자료의 오류도 수정한다.
- 성격 계열 rationale의 ‘성격의 관찰의’ 같은 어색한 결합을 교정한다.

필수 구현:

1. 조사를 붙이는 곳은 검토 가능한 한국어 어미 결합 함수를 사용하거나 어미에 의존하지 않는 문장으로 작성한다. 모든 문자열을 정규식으로 무차별 치환하지 않는다.
2. 받침 있는/없는 한글 용어의 은/는·이/가·을/를·이에요/예요를 필요한 범위에서 처리한다. 외국어·숫자 등 처리하지 않는 범위는 명시하고 임의 발음을 추측하지 않는다.
3. 검사 범위를 제목·본문·실천·evidence의 rationale/counterExample/limitation·공통 설명·근거 fact/theme/scope와 사용자에게 실제 생성되는 basis 문장까지 넓힌다.
4. 모든 일반 한국어를 자동 교정했다고 주장하지 않는다. 선정 용어 검사는 문법 오류 탐지이고, 문맥·어색함은 별도 편집 검토 항목이다.
5. 고정된 공통 계산 정책·한계 설명이 반복된다는 이유로 경고를 없애거나 전부 다른 말로 변형하지 않는다. 반복 검사에서 정책 설명과 고유 내용의 범위를 구분한다.

필수 검증:

- 양력 2000-01-09 10:30 → 연애사주 → ‘왜 이런 풀이인가요?’에서 ‘병화예요’ 또는 동등하게 자연스러운 문장.
- 양력 1992-05-15 10:30 → 2026년 올해 운세의 같은 패널에 ‘편재를’ 등 올바른 문장.
- 10일간과 10십성의 생성 설명을 표로 검사해 금·목처럼 받침 있는 정상 문장을 망가뜨리지 않음.
- 변경 전에는 새 검사가 실제로 오류를 탐지했고 변경 후 통과함을 기록.
- 실제 PDF에도 동일한 교정이 반영됨을 확인.

## 3단계 — CR-02 기간별 적용 이력을 일관되게 유지

현재 `FortuneResult.tsx`는 구간별 reading을 합치면서 `sections`는 병합하지만 `...readings[0]`의 `appliedRuleIds` 등은 첫 구간 값으로 남긴다.

재현 기준:

- 현재 날짜 2026-10-20, 출생 양력 1992-05-15 10:30, 올해 운세.
- 앞 구간은 편재 / `period-year-4`, 뒤 구간은 정관 / `period-year-7`.
- 실제 두 구간을 표시한다면 적용 이력에 두 ID와 각 구간을 모두 남겨야 한다.

필수 구현:

1. 기간 결과 조립을 검증 가능한 순수 함수로 분리한다. 컴포넌트 안에서 테스트되지 않는 병합식을 중복 사용하지 않는다.
2. 구간별 start/end, 관계 feature, 적용 원고 ID, 근거 ID, 필요한 원고 버전을 보존한다. 실제 사용한 feature의 범위도 추적할 수 있게 한다.
3. 전체 적용 원고 ID는 실제 표시된 원고들의 합집합과 일치시킨다. 문장 수 제한·중복 제거로 최종 출력에서 빠진 항목을 적용했다고 잘못 기록하지 않는다.
4. 제외 이유는 구간에 종속시켜 관리한다. 한 구간의 제외와 다른 구간의 적용을 모순된 전역 상태처럼 저장하지 않는다.
5. 화면의 현재 요약 구조를 유지하면서 근거 패널의 문장이 어느 구간에 관한 것인지 짧게 연결한다. 날짜·간지 상세 표기와 원고 이력의 연결을 잃지 않는다.
6. 공개 화면에 긴 내부 ID·디버그 JSON을 무조건 노출하지 않는다. 사람이 이해할 근거는 화면에, 재현용 구조화 데이터는 테스트·로컬 진단 산출물에 둔다. 진단을 서버 전송·브라우저 영속 저장으로 구현하지 않는다.

검사는 연간 입춘 전후·월간 절입 전후·단일 일간, 같은 원고가 여러 구간에서 나타나는 경우, 일간 미확정, 결과 길이 제한을 포함한다. 인쇄 전후 상세 열림 상태 복원과 기존 기간 안내도 보존한다.

## 4단계 — 계산 사실·전통 해석·생활 제안 분리

현 evidence는 근거 키 하나와 자유문 rationale·counterExample·limitation이다. 새 구조에서는 최소한 다음 세 층의 차이를 보존하라. 필요 없이 복잡한 그래프 DB나 서버를 만들지는 않는다.

- 계산 사실: 예를 들어 일간 신, 확정 천간의 식상 집계 2, 대상 구간 천간과 일간의 관계. 계산 정책과 직접 확인한 값.
- 해석 주장: 특정 상징을 어떤 관점으로 읽는지. 내부 편집 정책인지 확인된 문헌·독립 검토가 있는지 명시.
- 생활 제안: 그 관점으로 사용자가 해볼 수 있는 관찰·질문·행동. 생년월일로 실제 생활 사실을 알아냈다는 주장과 구분.

복합 조건을 도입할 때 여러 factual premise를 기록할 수 있어야 한다. 예를 들어 output>=2 AND wealth>=1을 쓰는 원고가 output 근거 하나만 가진 것처럼 축약되지 않게 한다. 각 전제는 조건 전체가 보장하고 필요한 feature도 확정돼 있어야 한다. 현재 `any`의 모든 분기가 근거를 보장해야 하는 성질을 약화시키지 않는다.

근거 정의의 kind·feature·operator·value가 서로 맞는지 검증하고, ID·출처가 존재한다는 검사와 주장 내용의 진실성을 구분한다. 외부 자료가 없으면 `internal-policy` 또는 그에 해당하는 상태를 유지한다. 가짜 책 이름·장절·쪽수·전문가·확인 날짜를 만들지 않는다.

버전 변경과 기존 210개 원고의 호환·마이그레이션 정책을 정한다. 수정하지 않은 원고를 새로 전문가 검토한 것처럼 버전을 덮어쓰지 않는다. 변경된 주장과 원고의 hash를 검토 기록과 연결한다.

## 5단계 — 자유문 반례를 실행 평가와 의미 검토로 나누기

현재 135개 중 105개의 counterExample이 본문 문단과 같다. 문장 안에 실질적인 한계·다른 행동 사례가 있으므로 ‘복사됨’만으로 모두 삭제하지 않는다. 다만 텍스트 길이가 30자를 넘는다는 검사를 반례 검증 완료로 취급하지 않는다.

두 종류를 분리한다.

### A. 엔진이 실행할 수 있는 반례

각 case에 case ID, 입력 feature 또는 합성 출생 입력, 예상·금지 원고/주장, 제한 안내, 검토 출처, 연결 문제 ID를 기록한다. 다음을 다룬다.

- 일간 null/누락, 관계 0/누락, 시간 미상, 절입일의 부분 확정.
- 일간 없이 관계나 기간 값만 잘못 전달한 입력.
- 동일 일간에서 관계 집계가 달라질 때의 결과 차이.
- 동수·최다 집계·배열 순서 변경·무관 feature 추가에 대한 안정성.
- 근거를 보장하지 않는 any 분기, 잘못된 basis/ranking field.
- 기간 병합의 전체·구간별 적용 이력과 표시 결과의 일치.
- 종합 1,800자 제한과 중복 제거 뒤 실제 출력이 사라지거나 진단과 달라지지 않는지.

실제 런타임 계산 결과의 불변식과 부분 feature로 만든 합성 테스트는 구분한다. 기존 부분 feature fixture에 없는 값을 0으로 채워 정상 입력처럼 만드는 방식으로 통과시키지 않는다.

### B. 사람의 의미 검토가 필요한 반례

‘같은 일간이어도 해당 생활 행동이 없는 사람’, ‘같은 관계명이어도 그 상황을 경험하지 않는 사람’, ‘문장과 반대 행동을 하면서도 성격 문제가 없는 사람’ 같은 사례다. 이를 생년월일에서 추론한 숨은 feature로 만들지 않는다.

검토자는 어떤 문장이 과도한지, 어떤 전제가 빠졌는지, 어떤 표현으로 낮춰야 하는지를 기록한다. 전문가가 검토하지 않은 것은 `pending`으로 남긴다. 실제 임상·학력·혼인·수입·성별·성적 지향 등 민감하거나 미확인 사실을 입력·출력에 추가하지 않는다.

현재 23개 수용 사례는 유지하고 변경 이유를 남겨 확장한다. 새 사례를 같은 구현자가 작성하면 독립 holdout이라고 부르지 않는다. 별도 검토자가 확정한 평가 자료가 있을 때만 역할과 버전을 명시한다. 학습을 수행하지 않으므로 편의상 데이터를 나눴다는 이유로 모델 학습/검증 완료라고 표현하지 않는다.

## 6단계 — 결과 전체의 편집 품질 평가

원고 개수·최소 글자 수·12글자 조각 유사도만으로 품질을 보장하지 않는다. 합성 프로필별로 조립된 전체 결과를 읽고 다음을 구분한 보고서를 만든다.

1. 내용 반복: core·relation·element를 합쳤을 때 같은 행동을 여러 번 권하지 않는가.
2. 행동 충돌: 한쪽에서 즉시 표현을 권하고 다른 쪽에서 기다림을 권할 때 조건이 독자에게 분명한가.
3. 근거 연결: 선택된 feature가 실제 문장의 소재와 연결되고 한계가 유지되는가.
4. 구체성: 장면·사용할 질문·실행 방법이 있고 주제와 시간 범위가 맞는가.
5. 범위: 계산하지 않은 월령·지장간·합충·강약·용신·대운이나 실제 미래 사건을 안다고 쓰지 않는가.
6. 사용성: 긴 문단이 늘어 390px 화면에서 읽기 어렵지 않은가. 필요한 결론과 이유가 연결되는가.

평가 항목별 예시와 미확인 상태를 남기고 종합 적중률 같은 단일 점수로 만들지 않는다. 의미 검토에서 확신할 수 없는 항목은 사람이 확인할 후보로 남긴다. 이미 검토된 공통 한계 문장을 과도하게 반복하지 않도록 공유 설명을 활용하되 숨기지는 않는다.

## 7단계 — 기존 feature를 이용한 소규모 복합 조건 시범

앞 단계가 통과한 뒤에만 시행한다. 기존 원고를 전부 새로 쓰지 말고 최대 6~10개 시범 규칙을 우선 준비한다. 대상은 연애·직업재물 등 차이를 설명하기 좋은 2개 주제로 제한해도 된다. 숫자를 채우려고 억지로 추가하지 않는다.

예시 비교는 같은 일간·같은 최다 식상일 때도 다른 보조 관계를 보는 것이다.

- 일간 신, 식상 2, 재성 1: 표현·초안을 실제 전달 과정과 시간·비용 계획에 연결하는 관찰 질문.
- 일간 신, 식상 2, 인성 1: 배운 내용을 설명·시도로 바꾸고 자료 이해와 실제 적용을 구분하는 질문.

위는 서비스 편집 설계 예시이며 고전의 확정 명리 규칙이 아니다. ‘식상생재가 성립했다’ 같은 용어로 확정하지 않는다. 현재 천간 관계 단순 집계가 구조의 성립·강약을 증명하지 않는다.

시범 원고는 조건·근거·반례를 먼저 만들고, 더 구체적인 조합이 우선될 때 기존 단일 관계 원고와 중복되지 않게 한다. 우선순위의 이유를 문서화한다. 동수 처리와 기존 규칙 순서의 결정성을 유지한다. 같은 생년월일에서 날짜와 관계없는 무작위 문장 순환으로 개인화를 꾸미지 않는다.

시범 원고의 입력·본문·미리보기는 별도로 제공하되 독립 의미 검토 전에는 draft로 두거나 명시적 실험 설정에서만 포함한다. 검토되지 않은 시범 원고가 일반 빌드에 자동 포함되면 실패다. 일반 빌드에서는 기존 원고가 그대로 fallback되는지 확인한다. 사용자에게 새 기능 확인을 맡긴 채 테스트 구현을 생략하지 않는다.

## 8단계 — 출처·검토 이력·배포 기준

현재 25개 근거는 내부 정책이다. 외부 근거가 필요하면 출처 등록 구조를 마련하고 확인 가능한 후보만 기록한다. 최소 필드는 출처 종류, 실제 제목·저자, URL/식별자, 확인한 위치, 확인일, 적용 정책, 사용 범위, 검토자, 상태다. 직접 열지 못한 자료는 확인 완료로 표시하지 않는다.

전문가 자료가 없는 상황에서도 코딩할 수 있는 검토 양식·로컬 CLI·schema·미리보기·대기 목록은 완성한다. 사용권이 불명확한 타 사이트 풀이를 복사하거나 대량 수집해 원고 수를 늘리지 않는다.

원고 검토 기록에는 reviewer 역할과 검토한 콘텐츠 hash/버전, 날짜, 대상 주장, 수정·반례, 상태를 연결한다. 자동 스크립트가 임의로 `human-reviewed`를 부여하지 않는다. 사람이 검토했더라도 미래 예측 정확성을 입증한 상태로 바꾸지 않는다.

피드백에는 메뉴·문장 ID/내용·오류 유형·원하는 설명 정도면 충분하다. 방문자의 실제 생년월일·개인 결과·식별 해시를 원격 수집하지 않는다. 재현은 합성 사례와 로컬 feature로 처리한다. 이번 작업에 서버 피드백 수집 기능을 새로 추가하지 않는다.

## 9단계 — 실행과 회귀 검사

실제 package.json과 일치하는 명령을 사용한다. 설치가 필요하면 lockfile로 설치한다.

- lint, strict TypeScript, 단위·통합 테스트.
- 콘텐츠 validate/lint/coverage/evaluate/preview.
- 정적 프로덕션 빌드와 실제 out/ 경로 확인.
- 기존 및 새 브라우저 검사.
- 실제 PDF 9개와 새 한국어·근거·기간 추적 시나리오.
- 시간 미상·윤달·DST·일간 미확정, 같은 입력 재사용·수정·삭제·새로고침.
- URL·요청 본문·콘솔·localStorage·sessionStorage·쿠키에 개인 입력을 새로 기록하지 않는지.
- 모바일 320/390px, 별자리 195px, 200% 글자 확대, 키보드·오류·공유·인쇄 복원.

tsx CLI의 IPC 제한이면 `node --import tsx scripts/content-tools.ts lint/coverage/validate/preview`처럼 개별 실행하고 전체 verify가 통과했다고 쓰지 않는다. build 별칭을 사용할 수 없으면 콘텐츠 검증·평가 후 같은 Next 빌드 단계를 실행한다. 브라우저·PyMuPDF 등이 없는 검사는 미검증으로 적고 가능한 나머지를 완료한다.

CI는 가능한 정적/콘텐츠 검사와, 환경을 준비했다면 브라우저·PDF 검사를 구분해 구성한다. 원격 Actions를 실제 실행하지 않았다면 로컬 통과만 보고한다. 새 Lighthouse·실기기 인앱·공개 호스팅을 테스트 없이 완료로 적지 않는다.

## 완료 조건

- CR-01·CR-02가 재현 가능한 실패 검사에서 해결된다.
- 표시 내용과 적용/제외 이력이 구간·원고·근거·버전까지 일치한다.
- 기존 210개와 새 시범/draft 개수, 근거 정의·공통 설명 개수가 분리된다.
- 해석의 사실성과 조건 적용의 정확성을 혼동하지 않는다.
- 새 복합 원고는 모든 조건의 전제를 보존하고 일반 운영에 미검토 상태로 자동 포함되지 않는다.
- 실행 중 LLM 호출·서버 DB·개인정보 영속 저장을 도입하지 않는다.
- 기존 계산 정책과 개인정보·화면 흐름의 회귀가 없다.
- 기존 평가 사례를 지워 통과시키지 않고 필요한 실패를 추가한다.
- 외부 배포·push·자동 학습을 실행하지 않는다.

최종 산출물은 수정 소스, 변경 요약, 버전·해시, 지적 대응표, 근거/검토 schema와 실제 예시, 평가 사례와 결과, 고정 입력의 이전/이후 출력 비교, 일반/실험 빌드 포함 정책, 실제 실행 명령·성공/실패/미검증 구분, 독립 검토자가 확인할 새 검토 묶음이다.

최종 설명에서는 무엇이 구체적으로 개선됐는지와 아직 전문가 자료·사용자 확인이 필요한 부분을 짧게 구분하라. ‘스스로 학습해 정확도가 올라갔다’, ‘전문가 수준’, ‘23/23이므로 적중률 100%’처럼 근거 없는 완료 표현을 쓰지 말라.

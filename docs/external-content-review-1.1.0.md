# 사주 콘텐츠 1.1.0 독립 검토

**판정: 개선 방향은 적절하고 실제 원고·조건 선택·근거 기록이 좋아졌다. 다만 문장 품질과 적용 이력의 정확성 2건을 수정한 뒤 다음 고도화를 진행하는 것이 좋다.** 이번 변경으로 사주 해석의 전문성이나 예측 정확도가 입증된 것은 아니다.

검토일: 2026-10-20. 첨부 ZIP과 두 개선 문서를 읽었고, 앱 소스 수정·외부 배포·모델 학습/API 호출은 하지 않았다. 테스트·독립 재현 스크립트와 검토 산출물만 별도로 만들었다.

## 1. 무엇이 실제로 개선됐나

현재 ‘데이터베이스’는 서버 DB가 아니라 버전이 있는 **JSON 원고·규칙·근거 저장소**다. 이 규모에서 SQL·벡터 DB를 도입하는 것이 다음 우선순위는 아니다.

제출 manifest 350개 파일의 해시를 직접 확인했다. 기준 원고 180개와 현재 210개를 ID별로 비교했으며 삭제는 없고 기존 105개 수정·30개 추가가 맞았다. 새·수정 원고 135개를 본문, 실천, 근거, 반대 사례, 한계까지 읽었다. 아래 길이는 제목·조언·근거 패널을 제외한 본문 기준이다.

| 계열 | 실제 확인 | 읽고 내린 판단 |
|---|---|---|
| 기본 70개 | 평균 453.4자, 70개 모두 evidence 연결 | 주제별 장면이 구체적이다. 같은 일간이라도 성격·연애·일·대인관계·솔로·마음돌봄의 질문이 달라졌다 |
| 기간 30개 | 평균 417.8자, 30개 모두 evidence 연결 | 하루 작업·월간 주별 점검·연간 분기 계획의 차이가 있다. 첫 두 문단은 기준본과 동일하고 뒤의 확장 문단이 바뀌었다 |
| 천간 관계 35개 | 평균 225.5자, 기존 5개 개정+다른 6주제 30개 추가 | 단일 일간 설명에 더해 확정 천간의 관계 집계를 이용하는 별도 보완 질문이 생겼다 |
| 오행 35개·가벼운 유형 28개 등 | 기존 75개 본문 유지 | 이번 135개 개선을 전체 210개 새 집필로 표현하지 않은 보고는 정확하다 |
| 근거 정의 25개 | 일간 10·기간 관계 10·확정 천간 집계 5 | 원고 수와 별도로 집계한 것은 적절하다. 내부 대응 정책이며 외부 원전 검증 자료는 아니다 |

의미 차이가 드러난 예를 들면, `core-careermoney-1`은 변경 요청의 시간·비용·품질과 업무 범위를 다루고, `core-careermoney-7`은 오류 수정과 추가 요구·인수 기준을 구분한다. `core-love-3`은 표정·짧은 답장에 대한 추측을 직접 질문과 구분하고, `relation-love-wealth`는 데이트 금액 외 예약·이동 준비의 수고를 다룬다. 단어만 바꾸어 같은 문장을 반복한 수준으로 판단하지 않는다.

실제 양력 1992-05-15 10:30과 2000-01-04 10:30은 둘 다 신금 일간이다. 직접 계산·브라우저 조회에서 전자는 식상 2개에 따른 `relation-love-output`, 후자는 식상·관성·인성이 각각 1개여서 정해진 동수 순서에 따른 `relation-love-order`가 선택됐다. 보완 내용과 근거 패널도 실제로 달랐다.

두 번째 사례를 ‘관성이 더 강하다’고 설명해서는 안 된다. 동수 때 편집상 고정 순서로 고른 것이다. 현재 화면은 이를 개수 우선·동수 순서·강약 아님으로 안내하며, 그 범위는 적절하다.

일간 미확정·집계 0·누락·일간 없이 관계값만 주어진 입력을 제외하고, `any` 중 근거를 보장하지 않는 분기를 거부하는 보완도 유효하다. 정적 원고와 일반 코드로 실행하는 저비용 구조를 유지한 점도 원래 목표에 맞는다.

## 2. 확정한 문제

소스 경로의 기준은 `/workspace/scratch/4656590025d3/saju-content-review-1.1.0/project/`다. 줄 번호는 제출본 기준이다.

### CR-01 / P2 — 근거 패널과 동적 설명의 한국어 오류가 검사에서 빠진다

**확신도: 높음.** 원고 ID는 `period-{day|month|year}-{1|4|5}` 9개와, 동적 일간/기간 설명을 사용하는 원고들이다.

근거 파일:

- `src/content/rules.json:4698,4872,4930,5278,5452,5510,5858,6032,6090`의 `evidence.rationale`.
- `src/domain/interpretation/knowledge.ts:22,24`의 `appliedFact()`.
- `scripts/evaluate-content.ts:15`는 문법 검사 입력을 `paragraphs`와 `practicalTips`로 제한한다.
- `src/domain/interpretation/engine.ts`의 `basisFor()`는 rationale을 실제 화면으로 전달한다.

인용과 재현:

1. 양력 **1992-05-15 10:30 → 올해 운세 → ‘왜 이런 풀이인가요?’**. 실제 화면에 “관계인 **편재을** 해당 시간 범위의 계획에 적용한…”이 보인다. 정상은 “편재를”이다. 같은 구조로 겁재을·정재을이 합계 9개 근거에 저장돼 있다.
2. 양력 **2000-01-09 10:30 → 연애사주 → 같은 패널**. “계산된 일간은 **병화이에요**”가 보인다. 정상은 “병화예요”다. 해당 템플릿은 화·토·수처럼 모음으로 끝나는 이름에도 고정 ‘이에요’를 붙인다.
3. 기간 설명도 편재·정재·겁재 뒤에 고정 ‘이에요’를 붙인다. 모음 뒤의 ‘예요’ 분기가 필요하다.

위 두 화면을 독립 브라우저로 직접 열어 재현했다. 230개 테스트·23개 편집 평가가 통과해도 실제 사용자 문장에 오류가 남는 사례다.

내부 근거 정의에도 `interpretation-bases.json:64,78,134,162,204,218`의 무은·기은·계은·겁재은·편재은·정재은이 있다. 이 `fact` 필드는 현재 `appliedFact()`가 그대로 출력하는 필드는 아니므로 모두 사용자 화면에 보인다고 주장하지 않는다. 다만 편집 기준 자료이므로 함께 고치는 것이 좋다. `성격의 관찰의`가 반복되는 rationale 15개도 “성격을 관찰하는…” 등으로 교정할 수 있다.

예상 동작은 저장 문장뿐 아니라 생성된 설명까지 자연스러운 한국어를 제공하는 것이다. 현재는 검사 밖 필드와 동적 문자열에 오류가 남는다.

수정 방향은 조사·서술격 결합 함수를 두거나 어미가 필요 없는 문장으로 바꾸고, 검사 범위를 제목·본문·실천·evidence·근거 정의·실제 생성 설명으로 넓히는 것이다. 선택한 용어의 조사 검사가 전체 문법 검사를 대신한다고 표시하지 말아야 한다.

### CR-02 / P2 — 여러 기간 구간을 합친 결과의 적용 원고 이력이 일부 누락된다

**확신도: 높음.** 사용자에게 출력되는 두 기간 본문이 사라지는 오류는 아니다. 데이터 검토·추적·향후 피드백 연결에 쓰일 결과 메타데이터의 문제다.

근거 파일:

- `src/components/FortuneResult.tsx:35–38`는 구간별 풀이를 만든 뒤 `sections` 등은 합치지만, `...readings[0]`에서 가져온 `appliedRuleIds`, `skippedRuleReasons` 등은 첫 구간 값으로 둔다.
- `src/domain/interpretation/engine.ts`는 개별 해석 결과에는 해당 결과의 `appliedRuleIds`를 정확히 생성한다. 누락은 화면에서 기간 결과를 합칠 때 생긴다.

재현은 날짜 **2026-10-20**, 출생 **양력 1992-05-15 10:30**, 메뉴 **올해 운세**다. 직접 계산한 결과는 다음과 같다.

| 구간 | 관계 | 실제 사용 원고 |
|---|---|---|
| 2026-01-01~입춘 전 | 편재 | `period-year-4` |
| 입춘~2027-01-01 전 | 정관 | `period-year-7` |

화면 본문과 근거 패널에는 둘 다 표시된다. 같은 소스의 병합식을 별도 스크립트로 재현하면 `sections`는 두 ID를 가지지만 `appliedRuleIds`에는 `period-year-4`만 남는다. 두 번째 구간의 적용 이력이 누락된다.

예상 동작은 전체 결과를 구성한 모든 원고를 정확히 추적하고, 같은 원고가 어느 구간에 적용됐는지도 구분하는 것이다. 현재 메타데이터를 사용자 피드백·재현 저장에 사용하면 실제 본문과 기록이 어긋날 수 있다. 현재 네트워크로 잘못 전송된 사례를 발견했다는 뜻은 아니다.

수정 방향은 구간 병합을 순수 함수로 분리하고 구간별 `start/end`, 관계, 원고 ID, 근거 ID를 보존하는 것이다. 전체 적용 ID는 실제 표시된 원고의 합집합으로 만들고, 제외 이유도 구간별로 다뤄야 한다. 한 구간에서 제외된 원고가 다른 구간에서 적용될 수 있기 때문이다. 근거 패널에는 필요할 때 짧은 구간 표기를 연결하면 독자가 서로 다른 관계가 함께 나오는 이유를 이해하기 좋다.

## 3. 결함과 구분해야 할 고도화 과제

### 반대 사례는 유용하지만 아직 실행 가능한 검증 데이터와 다르다

135개 중 **105개는 `evidence.counterExample`이 본문 한 문단과 정확히 같다**. 기본 원고 70개와 천간 관계 35개가 해당한다. 상당수 문단은 실제로 “이 조건이 아니면 다르게 읽어도 된다”는 내용을 담으므로, 복사됐다는 이유만으로 무효 원고로 판정하지 않는다.

그러나 자유문 반례를 저장했다고 그 반례로 엔진을 검사한 것은 아니다. 현재 `evaluation.ts`는 예상/금지 원고 ID, 제한 안내, 배열 역순의 동일성을 검사한다. 반례 문장에 적힌 실제 생활 조건이나 주장과의 모순을 의미 수준에서 판정하지 않는다. 기간 30개의 반례도 공통 범위 안내여서 별개의 부정 사례 30개를 확보한 것은 아니다.

다음에는 계산 전제에 관한 **기계 실행 반례**와 해석에 맞지 않는 **사람의 의미 검토 사례**를 구분해야 한다. 예를 들어 일간 null·관계 0·부정확한 조건 분기는 실행 평가로, “재성이 있어도 준비 부담과 관계없는 사람” 같은 사례는 전문가·편집자의 과도한 해석 방지 검토로 연결한다. 생활 행동을 생년월일에서 새로 알아낸 것처럼 엔진 feature로 만들지 않는다.

### 전문 해석의 근거는 여전히 내부 정책이다

`basisKey`와 `impliesBasis()`는 “갑 일간일 때 갑의 상징 원고를 선택했다”는 연결을 검사한다. 그 상징에서 성격·관계 질문으로 확장하는 해석의 타당성을 증명하지는 않는다. 현재 원고는 이를 창작 질문으로 공개해 정직하게 범위를 제한한다.

본격적인 명리 해설로 발전시키려면 출처가 확인된 원전·해설, 적용 학파·정책, 위치 정보, 독립 검토자의 수정·반례가 필요하다. 자료가 없으면 후보·미확인 상태로 남겨야 한다. 내부 정의에 외부 원전처럼 보이는 이름·쪽수를 덧붙이는 방식은 개선이 아니다.

### 개별 원고의 다양성에서 결과 전체의 유용성 평가로 넘어갈 필요가 있다

이번 원고는 주제별 장면이 다양해졌지만, 판단·계획·기록·역할·비용 확인이라는 생활 조언의 큰 틀을 공유한다. 예를 들어 `core-love-7`의 작은 약속과 기대 전달, `relation-love-order`의 연락·일정 약속은 하나의 결과에서 의미가 가까울 수 있다. 이는 사실 모순은 아니지만 독자가 느끼는 반복을 줄일 여지가 있다.

새 평가에서는 원고 하나뿐 아니라 조립된 결과의 중복, 상충하는 행동 제안, 이유와 본문의 연결, 길이 제한으로 빠지는 원고를 봐야 한다. 공통 계산 한계·주의 문구는 공유 설명으로 관리하고 불필요하게 전부 다른 문장으로 바꾸지 않는다.

### 아직 작고 내부적으로 작성된 평가 집합이다

23개는 구현자가 만든 수용 기준이며 독립적인 전문 정답이나 별도 검증 집합이 아니다. 기준본 12/23 → 현재 23/23은 이번에 새로 요구한 관계 원고와 evidence 조건을 충족했다는 뜻이다. 과거 제품 결함 11건을 발견했거나 예측 적중률이 상승했다는 의미가 아니다. 제출 문서도 이를 올바르게 구분했다.

## 4. 다음 고도화의 우선순위

| 순서 | 할 일 | 완료를 판단할 근거 |
|---|---|---|
| 1 | CR-01 언어 오류와 CR-02 기간 추적 수정 | 수정 전 실패 사례가 고정되고, 실제 화면·PDF·병합 결과에서 해결 |
| 2 | 계산 사실·전통 해석·생활 제안을 구조적으로 분리 | 각 문장 주장에 필요한 전제·출처·검토 상태·적용 한계가 연결 |
| 3 | 반례·메타모픽·결과 전체 평가 보강 | 누락/null/0, 동수, 입력 순서, 무관 feature, 기간 경계, 잘림을 별도 검사 |
| 4 | 이미 계산한 정보의 복합 조건을 소규모로 시험 | 같은 일간·같은 최다 관계여도 다른 보조 관계에서 설명의 차이를 납득할 수 있는 사례 |
| 5 | 독립 명리·편집 검토와 출처 자료 연결 | 누가 어느 버전의 어떤 주장을 확인했는지, 반대 사례와 미확인 상태 보존 |

복합 조건의 예는 ‘식상 2 + 재성 1’과 ‘식상 2 + 인성 1’이다. 현재 집계만 사용해 표현의 결과 연결과 배움·자료 활용을 다른 관찰 질문으로 설계할 수 있다. 이는 실제 창작 예시이며 전문가가 확정한 명리 규칙으로 제시하는 것이 아니다. 원고를 대량 생성하기보다 소수의 사례로 조건과 의미 차이를 먼저 검증하는 것이 좋다.

두 조건을 요구하는 원고에는 두 전제를 모두 기록해야 한다. `requires`만 추가하고 근거는 첫 조건 하나만 남기는 방식으로 확장하면 추적이 다시 약해진다.

월지 등 계산된 글자를 사실로 보여주는 것과 월령·왕쇠를 해석하는 것은 구분해야 한다. 지장간·합충·용신·대운을 추가하려면 계산 정책과 독립 기대값, 해석 출처를 먼저 준비해야 한다. 단순 개수에 가중치를 임의로 붙여 고급 명리 계산처럼 표시하는 방식을 권하지 않는다.

현재 규모에서는 파인튜닝·운영 중 RAG·서버 DB를 먼저 도입할 이유가 확인되지 않았다. AI는 개발과 초안 작성에 사용하고, 공개 실행은 검토한 정적 콘텐츠와 결정적 로직으로 유지할 수 있다.

## 5. 실제 실행한 검증

- 고정 lockfile로 `npm ci --ignore-scripts` 설치 성공.
- ESLint·TypeScript, 단위/통합 **230개 통과**.
- `npm run verify`는 tsx IPC 파이프 `EPERM`으로 콘텐츠 lint 단계에서 중단. 전체 명령 통과로 표기하지 않는다.
- 문서의 우회 방식 `node --import tsx scripts/content-tools.ts lint/coverage/validate/preview`를 각각 실행해 통과.
- `npm run content:evaluate` **23/23 통과**. 기준본에도 새 평가를 직접 적용해 **12/23**과 종료 코드 1을 확인. 그 실패는 비교 목적의 예상 결과다.
- 콘텐츠 검증·평가 후 동일한 `next build --webpack` 빌드 단계 성공, 정적 생성 작업 36개 완료.
- 실제 정적 빌드에 대해 Chromium 브라우저 검사 **57개 통과**.
- 새 실제 PDF **9개**의 문구 포함·부재 검사 통과, 닫힘/열림 텍스트 동일. 이 PDF 검사는 이번에 확인한 모든 한국어 오류까지 찾는 검사는 아니다.
- 별도 스크립트로 두 출생일의 같은 일간·다른 관계 선택, 잘못된 생성 문장, 기간 병합 이력 누락을 재현.
- 별도 브라우저 5개 시나리오에서 관계별 실제 본문·근거, 미확정 안내, 390px 가로 넘침, 고유 합성 별명의 요청·콘솔 노출, POST·저장소·쿠키를 확인. 가로 넘침·고유 별명 전송·비GET 요청을 발견하지 않았고 저장소·쿠키는 비어 있었다.
- 첨부 12쪽 화면 PDF의 연속 영역과 새 실제 화면을 열어 확인했다.
- 검토 후 manifest상의 앱 소스·테스트·스크립트 해시가 그대로임을 확인했다.

환경은 Linux, Node 24.19.0, npm 11.9.0, Chromium 153.0.8010.0이다. 모든 출생 입력은 합성 검증용이다.

이번에는 전체 달력 장기 비교, 실제 iOS/Android·Instagram 인앱, 공개 호스팅, 새 Lighthouse, GitHub Actions 원격 실행, OS 인쇄 UI·물리 프린터, 전문가 명리 검토를 수행하지 않았다. 근거의 외부 원전 대조나 예측 적중률 측정도 수행하지 않았다.

## 결론

이번 변경은 **원고를 길게 늘리는 데서 조건·근거·평가를 함께 관리하는 단계로 진전했다.** 현재 필요한 것은 무조건 더 많은 원고나 더 비싼 모델보다, 표시되는 언어의 교정·기간 추적의 정확성·반례 실행 평가·독립적인 해석 검토다. 두 확정 문제를 먼저 고치고, 소규모 복합 조건을 검토 가능한 단위로 추가하는 방향이 적절하다.

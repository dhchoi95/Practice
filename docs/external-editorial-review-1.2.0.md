# 하루사주 1.2.0 독립 검토와 한국어 원고 수정 지시문

검토일: 2026-10-21. 대상: 첨부 `content-review-package (1).zip`, `review-request.md`, `content-improvement-1.2.0.md`.

**판정: 이전의 조사 오류와 기간별 적용 이력은 개선됐다. 계산·원고·검토 구조의 개선 방향도 적절하다. 다만 서비스 문장에는 추상적인 설명, 반복되는 권유, 개발자 관점의 표현이 많이 남아 있다. 다음 작업의 우선순위는 원고 수나 모델 성능보다 한국어 편집과 결과 전체의 구성이다.**

이번에는 검토만 했다. 제출된 앱 소스·원고·테스트·스크립트를 고치거나 공개 배포하지 않았다. 독립 검사용 스크립트·실행 로그·화면·이 보고서만 별도로 만들었다. 아래 후반부의 실행 지시문은 사용자가 다음 Codex 작업에 전달하기 위한 것이다.

## 1. 이번 버전에서 확인한 변화

‘데이터베이스’는 현재 서버 DB가 아니라 조건·원고·근거·검토 기록을 담은 JSON과 코드다. 210개 규모에서 이 구조를 유지하는 선택은 원래의 무료·저비용 운영 목표에 맞는다.

패키지 무결성 목록 418개를 설치·실행 전에 대조했다. `baseline/rules-1.1.0.json`과 현재 원고를 ID별로 비교한 결과는 다음과 같다.

| 항목 | 독립 확인 결과 | 판단 |
|---|---|---|
| 정상 조건 원고 | 210개 | 시범 원고와 구분되어 있다 |
| 변경된 정상 레코드 | 36개 | 근거 문장 등의 교정이며, 본문·생활 제안 변경은 각각 0개다 |
| 나머지 정상 원고 | 174개 | 버전·검토 상태를 유지했다 |
| 공통 오행 설명 / 내부 근거 정의 | 5개 / 25개 | 정상 원고 개수에 합산하지 않는다 |

## 2. 말투에 대한 판단

사용자가 지적한 인상은 실제 원고에서 확인된다. 다만 문체만 보고 AI가 작성했는지 판별할 수는 없다. 여기서는 작성 주체를 추정하는 대신 **어떤 문장이 왜 읽기 어렵고 반복적으로 느껴지는지**를 평가했다.

전체 210개 원고의 본문 620문단을 검색·집계하고, 합성 입력 6개의 조립 결과 전체, 별도 초안 4개, 가벼운 유형 풀이와 미확정 안내를 읽었다. 대표 입력 5개는 390px 브라우저에서 직접 열었다. 모든 문장을 전문 한국어 교열자가 승인했다는 뜻은 아니다.

다음은 제목·생활 제안·근거 문장을 제외한 **본문만의 단순 문자열 집계**다. 해당 표현이 있다는 이유만으로 잘못된 문장으로 판정하지 않는다.

| 표현 | 출현 횟수 | 포함 원고 수 / 210 |
|---|---:|---:|
| 보세요 | 436 | 196 |
| 수 있어요 | 254 | 156 |
| 확인 | 224 | 138 |
| 상징 | 125 | 96 |
| 살펴 | 115 | 96 |
| 조건 | 103 | 69 |
| 소재 | 60 | 59 |
| 관점 | 41 | 38 |

문제는 ‘~해요’ 자체가 아니다. **상징을 소개하고 → 경험을 떠올리게 하고 → 두 개념을 구분시키고 → 확인·기록을 권하는 구조**가 여러 주제에서 반복된다. 친근한 운세 읽을거리보다 해석 방법을 설명하는 보고서나 업무 조언에 가까워지는 구간이 있다.

## 3. 수정이 필요한 사항

심각도는 이 서비스에서의 영향과 수정 우선순위다. P0는 서비스 중단·중대한 침해, P1은 핵심 결과의 중대한 오류, P2는 독해·의미·운영에 영향을 주는 수정 대상, P3는 국소적인 편집 개선으로 사용했다. 이번 검토 범위에서 새 P0·P1을 확인하지 못했다.

아래 소스 경로의 기준은 제출 ZIP의 `project/`다. 줄 번호는 제출본 기준이며 수정 후 달라질 수 있다.

수정 방향: 누가 무엇을 원하고, 어떤 말을 했으며, 무엇을 정하면 좋은지 동사 중심으로 쓴다. 전문용어가 실제로 필요한 계약·업무 맥락에서는 보존하되 짧게 풀어준다. 명리 용어의 정의와 내부 편집 방법은 근거 패널에 두고, 본문은 읽을거리로 편집한다.

예시: “내가 바라는 걸 상대에게 얼마나 자세히 말했는지부터 생각해 보세요. 내게 당연한 일도 상대는 모를 수 있어요.” 이 예시는 원문의 의도를 쉽게 옮긴 편집 시안이며 새 사주 사실이 아니다.

### KR-03 / P2 — 구간별 연간 풀이와 본문의 시간 범위가 어긋난다

**확신도: 높음. 계산 오류가 아니라 시간 범위의 표현 문제다.**

예상: 구간에 적용하는 조언과 한 해 전체에 관한 참고 조언의 범위를 독자가 구분할 수 있다.

수정 방향: 구간 원고는 ‘이 시기 / 시작하기 전 / 기간이 끝날 무렵’처럼 실제 표시 범위에 맞춘다. 연간 전체 계획을 유지하려면 별도 공통 연간 안내로 명시하고, 그 안내가 앞 구간의 계산에서 나온 개인 예측처럼 보이지 않게 한다. 모든 ‘연간’ 표현을 무조건 삭제하지 말고 각 문장의 실제 범위를 판단한다. 월간 절입 전후와 1일 구간도 함께 확인한다.

### KR-04 / P2 — 새 검토 기록을 추가해도 과거 stale 기록이 검사를 막는다

**확신도: 높음. 미래 편집 작업에 영향을 주는 검토 도구 문제다. 현재의 36개 기록 검사는 통과한다.**

근거:

- `scripts/review-content.ts:19–23`: 모든 기록을 현재 원고와 비교하고, 하나라도 stale이면 오류에 추가한다.
- `src/domain/interpretation/review.ts:9–18`: 과거 기록·대체 기록·현재 유효 기록을 구분하는 연결이 없다.
- `docs/content-schema-1.2.0.md:43`: 원고 변경 후 새 검토자는 “검토한 버전의 새 기록을 추가해야 한다”고 안내한다.

독립 재현: 앱을 수정하지 않고 메모리에서 `core-general-7`의 본문만 바꾼 가상 원고를 만들었다. 기존 기록은 보존하고, 새 원고의 올바른 해시를 가진 새 기록을 추가했다. 두 기록 모두 현재 스키마를 통과시켰다. 실제 CLI의 stale 판정식과 동일한 식으로 평가하면 기존 기록은 stale=true, 새 기록은 false이며 전체는 실패다. 이 검사는 복제한 값과 판정식을 실행한 것으로, 제출 원고를 변경해 실제 CLI를 다시 실행한 것은 아니다.

예상: 새 원고에 대한 기존 승인은 무효가 되지만, 과거 검토 이력을 남기고 현재 버전에 대한 새 검토를 기록할 수 있어야 한다.

실제: 새 기록을 추가하는 것만으로는 과거 기록의 오류가 해소되지 않는다. 다음 말투 편집 때 검토 이력을 덮어쓰거나 지우도록 유도할 수 있다.

수정 방향: `supersedes`나 명시적인 버전별 이력 모델 등으로 과거 보존과 현재 판정을 구분한다. 현재 원고에 필요한 검토가 없는 경우는 실패시키되, 정상적으로 대체된 과거 기록은 과거 이력으로 보고한다. 해시 변경 감지를 무시하거나 원본 검토 날짜·이름·해시를 새 값으로 덮어써서는 안 된다. 새 기록을 만들었다고 독립 검토 완료로 자동 승격해서도 안 된다.

### KR-05 / P3 — 제목·근거·초안에 작성 방법이 드러나는 표현이 남는다

**확신도: 높음. 일부는 내부 검토 자료이므로 공개 화면 문제와 구분한다.**

근거:

- `src/content/rules.json:3305` 등: “관계에서 주고받는 표현에 더하는 목의 관점”.
- 같은 파일 `:7734`: “토 0개는 결핍의 진단이 아니에요”.
- `src/components/FortuneResult.tsx:65`: 독립 작성·자동 형식 검사·독립 명리 검토 상태를 긴 문장으로 설명한다.
- `content-review/compound-drafts.json:39` 등: 본문에 “천간 집계 조합을 … 질문의 선택 기준으로만 사용해요”가 들어간다. **초안 4개는 현재 공개 빌드에 들어가지 않는다.**

재현: 위 일반 입력의 결과 제목·근거 패널을 확인한다. 초안은 `npm run content:compound`로 만든 로컬 미리보기에서만 읽는다.

예상: 제목은 이 항목에서 읽을 내용을 쉽게 알려준다. 한계·출처 상태는 사실대로 이해할 수 있다.

실제: 일반 제목이 분류명이나 논문의 소제목처럼 길다. 일부 문장은 독자를 향한 풀이보다 원고 생성 방식을 설명한다. 반대로 ‘미검토’ 등 필요한 설명을 전부 없애면 신뢰 상태를 오해시킬 수 있다.

수정 방향: 예를 들어 제목은 “익숙한 만남에 작은 변화를”, “토가 0개면 부족한 걸까요?”처럼 짧고 구체적으로 검토할 수 있다. 모든 제목을 질문형으로 통일하지 않는다. 내부 조건 수·선택 기준은 근거 층에 둔다. 공개 근거는 계산한 사실·해석에 사용한 관점·아직 모르는 것을 구분해 쉽게 쓴다. ‘검증됐다’고 잘못 받아들이게 하는 표현은 만들지 않는다.

### KR-06 / P3 — 연애 문장이 현재 상대가 있다는 상황을 자주 전제한다

**확신도: 중간~높음. 메뉴가 연애인 것은 맞지만 입력으로 현재 교제 여부를 받지는 않는다.**

근거: `src/content/rules.json`의 `core-love-7`, `relation-love-output`, `element-0-love`. `content-review/semantic-cases.json`에도 관계 상황의 누락을 검토할 후보가 있다.

재현: 연애사주에서 1992-05-15 10:30을 입력한다. 같은 입력이라도 현재 교제 여부는 알 수 없는데, 기념일·상대가 편한 표현·함께할 활동의 예산을 연속으로 제안한다.

수정 방향: 관계가 필요한 문단에서만 “만나는 사람이 있다면”, “함께 하고 싶은 일이 있다면”처럼 적용 상황을 짧게 밝힌다. 모든 문장마다 조건을 반복하거나 현재 상대의 마음을 추정하지 않는다. 이를 해결하려고 연애 상태·성별·성적 지향 같은 입력을 새로 수집할 필요는 없다.

# Codex에 전달할 수정 지시문

아래 ‘실행 지시 시작’부터 끝까지를 현재 프로젝트와 함께 전달한다. 이 검토 문서의 과거 절대 경로를 그대로 가정하지 말고 실제 저장소를 찾는다.

## 실행 지시 시작

너는 하루사주 기존 프로젝트의 한국어 편집자이자 콘텐츠 엔지니어다. 이번 목표는 원고의 뜻과 계산·개인정보 정책을 보존하면서, 한국어 독자가 자연스럽게 읽는 문장과 중복이 적은 결과를 만드는 것이다. 계획이나 문체 제안만 남기지 말고 허용 범위의 편집·구현·검증·변경 보고까지 완료하라.

현재 기준은 콘텐츠 1.2.0, 규칙 엔진 2.0.0, 정상 원고 210개, 공통 설명 5개, 내부 근거 25개, 별도 draft 4개다. 실제 저장소 상태를 다시 확인하고 다르면 차이를 기록한다. 최신 상태와 기존 미완료 변경을 보존한다.

외부 배포·원격 push·도메인 구입·결제·외부 메시지·유료 모델 API·자동 학습은 하지 않는다. 서비스 실행 중 LLM을 호출하지 않는다. 서버 DB·벡터 DB·로그인·관리자 서버·RAG·챗봇을 추가하지 않는다. 로컬에서 재현·검토 가능한 결과를 만든다.

### A. 먼저 읽고 기준을 고정하라

### B. 편집 범위와 보존할 경계

다음은 전부 **검토 범위**다. 이미 자연스럽거나 필요한 정확한 문장은 유지할 수 있다. 모든 필드를 바꾼 것으로 숫자를 채우지 않는다.

1. 정상 210개의 제목·본문·생활 제안.
2. 사용자에게 표시되는 evidence·동적 근거 문장·공통 5개 설명·25개 근거 정의의 공개 텍스트.
3. 홈·입력·결과·오류·시간 미상·새로고침·공유·인쇄·소개·출처 안내의 한국어.
4. 띠·별자리·혈액형처럼 가벼운 유형 풀이와 날짜별 변주가 있다면 그 문장.
5. 별도 초안 4개의 문장. 초안은 계속 draft로 두고 일반 빌드에서 제외한다.

문체 수정만으로 다음을 변경하지 않는다: 계산 정책, 달력·윤달·DST·절입 계산, 일주·일간 확정 범위, 오행 집계 방법, rule ID, condition, requires, exclusions, priority, specificity, ranking, 동수 정책, draft 포함 정책. 부득이한 구조 변경은 별도 변경으로 설명하고 재현·회귀 검사를 추가하라. 기능 개선을 핑계로 새 해석을 끼워 넣지 않는다.

‘사람이 쓴 것처럼’이란 한국어 편집 품질을 말한다. 실제 사람이 검수했다고 거짓 표시하거나, 전문가 자격·상담 경력·개인 경험담·사용자 후기·원전 인용을 만들어내라는 뜻이 아니다. AI 탐지기를 속이는 목표·점수·문자 섞기·의도적인 오타를 사용하지 않는다.

### C. 문체 기준

독자는 20~60대의 일반 한국어 이용자다. 차분하고 다정한 해요체를 유지한다. 설명은 분명하게 하되 가르치거나 숙제를 주는 태도를 줄인다. 반말·유행어·과한 감탄·애교·점술가 흉내·공포·훈계는 쓰지 않는다.

문장의 출발점은 독자가 겪을 법한 장면이다. ‘표현의 수용 범위’, ‘정보의 양’, ‘자원 배분의 관점’보다 무슨 말을 했고, 어떤 부탁이 늘었고, 시간이나 돈이 얼마나 드는지를 쓴다. 추상명사를 동의어로 치환하는 수준에서 끝내지 말고 문장 자체를 다시 구성하라.

명리 용어가 꼭 필요하면 짧게 풀어준다. 본문 모든 문단을 ‘X의 상징을 Y의 소재로 읽으면 Z의 관점’으로 시작하지 않는다. 선택 기준·원고 생성 과정·집계 조합·검토 도구 설명은 적절한 근거·안내 층으로 옮긴다. 본문에는 독자가 읽을 내용을 남긴다.

‘상징·관점·소재·확인·조건·기준·범위·구분·구체적·함께’는 금지어가 아니다. 뜻이 분명하고 필요한 곳에서는 쓴다. 같은 문단에 여러 개 쌓여 실제 행동이 가려지는지 살핀다. ‘~해요’, ‘~수 있어요’, ‘~보세요’도 금지하지 않는다. 문제는 한 결과에서 모든 문장이 같은 역할과 리듬을 갖는 것이다.

모든 문장을 ‘~세요’로 끝내지 않는다. 짧은 설명, 적용 상황, 한 가지 제안을 자연스럽게 연결한다. 종결어미만 무작위로 바꾸거나 ‘~랍니다 / ~죠 / ~겠지요’를 기계적으로 섞지 않는다. 문단 수·문장 수를 모든 원고에 똑같이 강제하지 않는다.

한 문장은 가능하면 한 가지 생각을 전달한다. 긴 명사구·겹친 조사·피동·불필요한 ‘~것 / ~부분 / ~측면 / ~과정’은 줄인다. 다만 기계적으로 삭제해 뜻을 훼손하지 않는다. 소리 내어 읽었을 때 한국어 독자가 평소 쓸 법한 표현인지 검토한다.

계속 질문만 던지는 상담지로 만들지 않는다. 첫 문장에서 이 항목이 다루는 내용을 알려주고 필요한 이유를 짧게 설명한다. 직접 진단하지 않으면서도 구체적으로 쓸 수 있다. 예: ‘마감이 가까운데도 고칠 곳만 보인다면, 이번에 꼭 고칠 부분부터 정해 보세요.’ 이는 적용 상황이 있는 제안이지 그 사람이 실제 완벽주의자라는 진단이 아니다.

숫자는 필요한 경우만 사용한다. 모든 조언을 ‘하나·두 가지·세 개’로 만들지 않는다. 마지막 제안은 짧고 실행 가능한 핵심만 남긴다. 본문을 한 번 더 길게 요약하거나 새 할 일을 덧붙이지 않는다.

### D. 의미·불확실성·개인정보를 보존하라

계산 사실 / 내부 해석 / 생활 제안을 계속 구분한다. ‘식상 2개’는 확정 천간의 단순 집계이며 강약·용신·식상생재 구조의 성립이 아니다. ‘토 0개’는 결핍 진단이 아니다. 문장을 자연스럽게 바꾼다고 이런 제한을 제거하지 않는다.

반대로 모든 문단 끝에 경고를 붙여 같은 설명을 반복하지 않는다. 공통 정책은 한 곳에 분명히 설명하고, 개별 문장에는 그 상황에서 필요한 한계만 남긴다. 본문은 확정적 예언처럼 바꾼 뒤 경고 하나로 덮는 방식도 금지한다.

현재 교제·혼인·직업·재산·학력·건강·성별·성적 지향·상대의 마음을 추정하지 않는다. 관계가 전제되는 문단은 ‘만나는 사람이 있다면’, ‘함께 정할 일이 있다면’처럼 필요한 곳에서 조건을 밝힌다. 같은 조건을 문장마다 반복하지 않는다. 상대가 없다면 억지로 할 행동을 만들어주지 않는다. 이를 해결하기 위해 개인정보 입력을 추가하지 않는다.

불확실한 일간·시주는 그대로 제한한다. 시간이 없으면 0시나 임의 값을 채우지 않는다. ‘결과가 부족하니 더 정확한 유료 상담이 필요하다’는 유도 문구를 만들지 않는다.

혈액형·띠·별자리의 가벼운 읽을거리와 사주 계산은 구분한다. 특히 혈액형으로 성격·능력이 과학적으로 확정된 것처럼 읽히지 않게 한다. 외로움·솔로·마음돌봄에서 낙인이나 의학적 진단을 만들지 않는다.

### F. 결과 전체를 편집하라

우선 주제와 원고 유형을 고르게 포함한 대표 12~16개를 골라 문체 기준과 수정 전후를 작성하라. 13개 메뉴가 검토에서 빠지지 않게 하되, 한 원고를 메뉴 수로 중복 집계하지 않는다. 이 단계에서 계획만 남기고 멈추지 말고 나머지 편집과 검증을 이어간다.

그다음 모든 대상 원고를 검토하고 실제 변경이 필요한 문장을 편집한다. 특히 기존 6개 합성 입력의 전체 결과를 수정 전후로 모두 읽는다. 필요하면 다른 일간·시간 미상·연초·월초·절입일의 합성 입력을 보충하라.

종합 결과에서는 기본·성격·직업이 모두 ‘완성도·마감’을 반복하지 않게 하라. 연애·대인관계에서 ‘기대·약속’이 반복될 때 각 항목의 새 정보가 무엇인지 설명할 수 있어야 한다. 단순히 ‘기준’을 ‘원칙’으로 바꾼 것은 의미 차이가 아니다.

완성도를 지키라는 조언과 초안을 먼저 보여주라는 조언이 함께 있으면 적용 순서를 밝혀라. 필수 오류를 고친 뒤 작은 범위로 의견을 받는 것처럼 실제로 양립하는 조건이어야 한다. 상충하는 문장을 연결어만 추가해 숨기지 않는다.

문자열이 다르다고 의미가 다르다고 판정하지 않는다. 자동 유사도·빈도는 검토 후보를 찾는 보조 도구로만 사용한다. 반복 검사에서 계산 정책·한계 문장을 고유 내용과 구분한다.

가능하면 기존 원고의 역할과 문단 구성을 편집해 해결하라. 런타임 요약 모델을 넣지 않는다. 조립 로직을 바꿔야 하면 변경 범위를 작게 유지하고, 숨긴 원고·잘린 문단·선택되지 않은 생활 제안의 이력을 적용했다고 남기지 않는다. 별도의 편집 요약을 만들었다면 원문 그대로 출력된 것처럼 추적하지 않는다. 표시 내용·주장·원고·버전의 연결이 실제 출력과 맞아야 한다.

### G. 기간 문장과 화면 연결을 수정하라

2026-10-20 한국시간 고정, 양력 1992-05-15 10:30의 연간 입력을 반드시 재현하라. 앞 구간은 1월 1일~입춘 전 약 한 달이고 뒤는 입춘~다음 1월 1일 전이다.

‘앞 구간’이 독자에게 상반기처럼 읽히지 않게 필요한 짧은 날짜 설명을 본문 가까이 제공할 수 있다. 정확한 시각은 기존 상세에 유지한다. 기본 UI를 새 디자인으로 바꾸거나 펼침 패널을 억지로 모두 열어놓지 않는다.

각 구간에 ‘분기마다·연말·연간 계획’이 붙을 때 실제 적용 기간과 맞는지 판단하라. 구간용 문장과 양력 한 해 전체의 공통 조언을 섞지 않는다. 올해·이번 달·오늘 각각의 시간 단위가 자연스러워야 한다. 연도나 월을 고정 문자열로 하드코딩하지 않는다. 구간의 시작·끝과 한국시간 정책은 계산 계층의 실제 값에서 가져온다.

### H. 검토 이력의 과거 보존과 현재 판정을 분리하라

문체 편집을 시작하기 전에 이번 검토의 KR-04를 재현하고 필요한 최소 수정을 하라. 현재 코드는 과거 기록도 새 원고와 비교해 무조건 stale 오류로 만들므로, 새 기록을 추가해도 통과할 수 없는 구조다.

버전별 기록이나 `supersedes` 등 적절한 구조로 과거 이력과 현재 원고의 검토 상태를 구분한다. 방법은 저장소에 맞게 정하되 다음은 필수다.

- 과거 기록은 대상 원고 해시·주장 해시·날짜·검토자·상태와 함께 보존한다.
- 새 원고에 과거 승인이 그대로 유효해지지 않는다.
- 새 원고에 필요한 검토가 없거나 현재 검토의 해시가 어긋나면 탐지한다.
- 올바른 새 기록을 추가하고 과거를 대체한 경우 정상적인 편집 흐름이 가능하다.
- 잘못된 대체 대상·순환·다른 원고를 대체하는 연결을 허용하지 않는다.
- 작성자 교정을 독립 검토 완료로 자동 바꾸지 않는다.
- 검토하는 claim이 해당 rule에 속하는지도 확인한다. 전체 claim 목록에 같은 ID가 존재하는 것만으로 승인하지 않는다.

현재 정상 자료, 수정 후 재검토 필요, 정상 대체 이력, 잘못된 대체 연결에 관한 의미 있는 검사를 작성하라. 과거 기록을 삭제하거나 새 해시로 덮어써서 통과시키지 않는다. 도구가 편집 문장의 자연스러움을 자동 승인한 것처럼 표현하지 않는다.

### I. 버전과 출처를 관리하라

실제로 바뀐 원고·공통 설명·공개 주장만 새 버전과 변경일을 기록한다. 변경하지 않은 원고를 전부 새로 집필·독립 검토한 것처럼 올리지 않는다. 안정된 ID를 유지하고 이번 수정 대상과 기존 지적 ID를 연결한다.

원고를 고치면 해당 해시와 검토 연결을 갱신하고 필요한 재검토 상태를 남긴다. 내부 편집 정책은 내부 정책으로 유지한다. 외부 원전을 이번 작업에서 직접 확인하지 않았다면 확인일·쪽수·저자·검토자·verified 상태를 만들어 넣지 않는다. 명리 전문가가 검토하지 않은 것을 human-reviewed로 만들지 않는다.

독립 편집 검토와 명리 검토를 별도 범위로 표시한다. 문체가 자연스러워졌다는 것은 전통 해석이나 미래 예측이 검증됐다는 뜻이 아니다.

### J. 검증과 제출물

가능한 기존 검사를 실제로 실행하라. 기준은 단위·통합 283개, Chromium 60개, 실제 PDF 11개이며 개수는 현재 저장소에서 다시 확인한다. 문구가 바뀌어 의미가 같은 기대 텍스트를 조정해야 한다면 이유를 기록한다. 독해 문제를 고치면서 이전의 어색한 문구를 통과시키기 위해 테스트를 유지하는 것도, 검사를 지워 문제를 숨기는 것도 피한다.

검사할 사항:

1. 저장 문장뿐 아니라 생성되는 조사의 정상 동작, 10일간·10십성, 한글 외 발음을 추측하지 않는 정책.
2. 동일 입력·시점·버전에서의 결정성, 동수, 누락/null/0, 잘못된 any, 초안 미포함과 기존 fallback.
3. 종합 길이 제한·중복 제거 후 실제 표시 원고·문단·제안과 trace 일치.
4. 연·월·일 구간별 본문·날짜·근거·이력의 일치. 연간 앞 구간의 기간 표현을 다시 확인.
5. 시간 미상·일간 미확정·윤달·DST·수정·삭제·재입력·새로고침의 기존 회귀.
6. 입력 → 결과 → 근거 펼침 → 다른 풀이 → 인쇄까지 390px, 320px, 확대 상태로 읽기. 띠·별자리·혈액형 메뉴도 확인하고, 기존 별자리 195px 검사를 보존.
7. 실제 PDF에서 교정 문장이 보이고 필요한 표·근거·기간이 빠지지 않음. 인쇄 전후 펼침 상태 복원.
8. 요청·URL·콘솔·브라우저 저장소·쿠키에 출생정보·별명·개인 결과를 새로 남기지 않음. 공유는 일반 메뉴 링크만 제공.
9. 검토 이력의 과거 보존·현재 판정. 편집 후 오래된 승인을 새 버전 승인으로 재사용하지 않음.

빈도 집계는 같은 범위로 수정 전후를 비교하되 수치를 억지로 0으로 만들지 않는다. ‘AI 말투 90% 제거’ 같은 검증 불가능한 점수는 쓰지 않는다. 특정 표현이 남아야 한다면 뜻과 위치가 적절한지 실제 결과로 설명한다.

환경 제한이 있으면 명령·원인·우회 실행을 구분한다. tsx IPC 제한이면 `node --import tsx scripts/content-tools.ts MODE`를 개별 실행하고 전체 verify 통과라고 쓰지 않는다. 실제 스마트폰·인스타 인앱·공개 호스팅·원격 CI·전문가 확인을 하지 않았으면 미실행으로 남긴다. 사용자에게 검증을 떠넘기고 가능한 로컬 검사를 생략하지 않는다.

최종 산출물:

- 수정된 소스와 콘텐츠, 작은 범위의 실제 변경 목록.
- 한국어 편집 기준과 대표 수정 전후 최소 20쌍. 원고 ID·필드·수정 이유·뜻과 한계의 보존 여부를 적는다.
- 실제 변경·유지 원고 수, 버전·해시, 검토 이력 마이그레이션과 재검토 상태.
- 6개 합성 프로필의 수정 전후 전체 결과와 반복·행동 순서·시간 범위·근거 연결에 대한 편집 메모.
- 각 메뉴를 빠뜨리지 않았다는 검토 목록. 검토했다고 모든 문장을 변경한 것으로 계산하지 않는다.
- 실제 화면·실제 PDF·테스트 결과, 실행/실패/우회/미실행 구분.
- 이번 독립 검토 KR-01~06의 대응표. 해결됐다고 주장할 때 재현 입력과 결과를 연결한다.
- 다음 검토자가 원고·조건·출처·검토 이력·최종 화면을 직접 대조할 수 있는 로컬 검토 묶음.

최종 설명은 사용자가 알아야 할 변화와 남은 한계를 한국어로 짧게 정리하라. ‘사람이 썼다’, ‘전문가 검증 완료’, ‘더 잘 맞는다’, ‘스스로 학습했다’ 같은 근거 없는 표현은 쓰지 않는다.

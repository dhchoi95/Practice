# 설계: 햄버거 매장 운영 관리

## 목적과 초기 운영

첫 적용 대상은 햄버거 한 종류를 판매하는 단일 매장이다. Owner 한 명과 Staff 한 명이 사용하며, Owner가 영업 종료 후 그날의 판매 합계를 입력한다. 반응형 한국어 웹으로 모바일에서도 재고, 예약, 시설 업무를 처리한다. Owner는 초대 링크를 만들어 직원에게 따로 전달한다. 앱은 초대 이메일을 보내지 않는다. 공개 회원가입, 결제/구독, 실제 POS·은행·예약 플랫폼 연동은 초기 범위에 없다. 코드에는 seed된 데모 매장에서만 사용할 수 있는 결정적 Mock POS 일합산 가져오기가 있다. 실제 판매 기록이 있는 날에는 데모 자료를 넣지 않는다. 자동 기능은 애플리케이션 코드와 데이터베이스 규칙으로 제공하며 런타임 LLM API를 호출하지 않는다.

## 화면과 주요 흐름

- **로그인:** 초대받은 계정만 로그인한다. 초대 링크는 일회 사용이며 48시간 후 만료된다. Owner는 운영 설정을 관리하고 Staff는 허용된 재고·예약·시설 업무를 처리한다.
- **대시보드:** 오늘 입력 여부와 매출, 예약, 부족 재고, 미완료 발주, 시설 점검을 요약한다. 입력 전 매출은 0원 매출과 구분한다.
- **매출:** 영업일별 햄버거 수량, 단가, 할인, 환불을 기록하고 수량 정정 사유를 남긴다. 일합산 기록의 동일 재시도는 한 번만 반영한다. 매출 확정 시 해당 영업일에 유효한 레시피로 재고를 차감한다. 금액 환불은 재고를 복원하지 않는다. Mock POS 가져오기는 seed marker가 있는 데모 매장에서만 허용하고 해당 날짜에 판매 기록이 없을 때 실행한다. 같은 가져오기 재시도는 이후 판매 정정이 있어도 이중 차감하지 않는다.
- **재고:** Owner는 재료, 단위, 최소/목표량, 포장 단위, 기준 단가와 레시피를 관리한다. 입고, 사용, 폐기, 실사는 현재 잔고와 연결된 원장 이력으로 남긴다. 레시피 변경은 새 버전을 만들어 과거 판매 기록을 보존한다.
- **발주:** 부족 수량에 확정·부분 입고 발주의 미입고량과 포장 단위를 반영해 추천한다. Owner는 발주 초안을 만들고 확정·취소 및 부분 입고를 기록한다. 입고 재시도는 중복 재고 증가를 만들지 않는다.
- **예약:** 전화나 외부 서비스로 접수한 예약을 수동 등록하고 변경한다. 날짜, 인원, 경로, 테이블 및 상태를 관리한다. 기본 예약 시간은 90분이며, 동일 테이블의 겹치는 시간과 정원 초과를 막고 취소·노쇼는 자리를 해제한다.
- **시설·비용:** Staff는 이상을 등록한다. Owner는 시설과 작업 상태를 관리하고 수리 완료 및 수리비를 입력한다. 완료 처리 시 작업 이력과 지출 장부 항목을 한 트랜잭션에 저장하고, 같은 완료를 재전송해도 비용을 중복하지 않는다. 수리비는 Staff에게 노출하지 않는다.
- **장부:** 판매 기반 매출과 별도 수입·지출을 보여준다. 오입력 취소는 기존 거래를 지우지 않고 반대 방향의 취소 거래를 남긴다. 운영 추정 손익은 회계·세무 결과나 은행 잔액으로 표시하지 않는다.

PC에서는 매장 화면을 사이드 탐색으로, 모바일에서는 상단 고정 가로 탐색으로 구성한다. 매출·재고·예약처럼 자주 쓰는 작업을 메뉴 깊숙이 숨기지 않는다. 입력 폼은 단위와 통화 단위를 표시하고, 저장 성공·검증 오류를 명확히 보여준다. 직원 초대 링크는 Owner가 확인해 전달한다.

주요 업무 흐름은 `일마감 판매 입력 → 검토/확정 → 재고 원장 반영 → 부족품 발주 → 입고`이다. 예약과 시설 이상은 업무와 독립적으로 등록되며 대시보드에 미처리 상태가 나타난다. 화면은 목록 보기만 제공하는 대시보드가 아니라 생성, 조회, 수정, 취소/비활성 및 상태 변경을 역할별로 실행할 수 있어야 한다.

## 시스템 구조

단일 Next.js App Router 애플리케이션에서 화면과 서버 Route Handler를 제공하는 모듈형 단일 앱 구조다. `/[storeId]/[section]`의 공통 작업 화면은 대시보드, 매출, 재고, 발주, 예약, 시설, 장부, 설정을 제공한다. 업무 API는 `/api/stores/[storeId]` 아래에서 입력을 검증하고 로그인 계정의 활성 StoreMember 및 역할을 확인한 뒤 Prisma를 통해 PostgreSQL에 접근한다. 실제 POS·은행·외부 예약 시스템은 연결하지 않는다. 데이터베이스는 로컬 개발 및 운영 환경의 PostgreSQL 17 계열이다.

인증은 credentials 로그인, bcryptjs 비밀번호 해시(cost 12), `jose`로 서명한 8시간 JWT 세션 쿠키를 사용한다. 쿠키는 HttpOnly와 SameSite=Lax이며 운영 환경에서 Secure로 설정한다. 서명 키는 `AUTH_SECRET`이며 최소 32글자를 요구한다. 인증이 필요한 각 요청은 현재 활성 계정과 매장 멤버십을 다시 확인해 비활성화된 멤버의 기존 세션 접근을 차단한다. 매장 API는 경로의 storeId가 현재 사용자의 활성 매장 멤버십과 일치하는지 검사한다. 화면에서 메뉴를 숨기는 것과 별도로 서버 권한을 검사한다. 로그인 및 상태 변경 요청은 Origin 검사를 수행하고 로그인 실패 횟수 제한을 적용한다. 로그인 제한은 앱 프로세스 메모리에 저장하므로 여러 인스턴스 배포에는 공유 제한 저장소가 필요하다. 초대 토큰은 해시 저장, 48시간 만료, 일회 사용을 적용한다.

API는 `/api/auth/{login,logout,invitations/accept}`, `/api/me/stores`, `/api/stores/[storeId]/dashboard`, 메뉴/레시피, 재료와 재고/원장, 일합산 매출·정정·환불·데모 POS 가져오기, 예약·테이블, 공급업체·발주 추천·발주/입고, 시설·수리 이력, 재정 원장·취소·합계, 멤버/초대로 나뉜다. 화면 컴포넌트에서 DB를 직접 조회하지 않는다. 각 역할에서 실제 노출되는 동작은 [requirements.md](requirements.md)의 권한 표와 일치해야 한다.

## 데이터와 정확성 규칙

Prisma 모델은 `Organization`, `Store`, `User`, `StoreMember`, `StoreInvitation`, `Menu`, `Ingredient`, `Recipe`/`RecipeItem`, `Inventory`/`InventoryTransaction`, `DailySale`/`SaleEvent`, `DiningTable`/`Reservation`, `Supplier`, `PurchaseOrder`/`PurchaseOrderItem`/`PurchaseReceipt`, `Facility`/`MaintenanceRequest`/`MaintenanceHistory`, `FinancialTransaction`, `AuditLog`으로 업무 데이터를 표현한다. Store는 모든 운영 자료의 범위다. 사용자-매장 역할은 StoreMember로 표현하며 모든 조회와 변경은 인증된 매장 범위로 제한한다. 판매, 재고 변동, 입고 및 비용은 반복 요청에도 중복 반영되지 않도록 고유 출처 키/멱등성 규칙을 둔다. 현재 재고는 변동 이력과 일치해야 한다. 판매 시점의 메뉴·레시피 정보가 과거 자료에 영향을 주지 않도록 스냅샷 또는 버전을 보존한다.

원화는 정수 원 단위로 처리하고 API 직렬화 시 큰 정수의 안전성을 보장한다. 수량과 단가는 정밀 Decimal 값으로 처리한다. 한국 시간대는 `Asia/Seoul`, 초기 영업일 경계는 자정이다. 첫 레시피는 바로 유효하고 다음 버전은 이후 첫 한국시간 자정부터 적용한다. 매출과 Mock POS는 영업일의 다음 자정 이전에 유효한 버전을 선택하고 기존 판매 정정은 저장된 레시피 snapshot을 사용한다. 예약 시간 충돌, 재고 부족, 확정 후 발주 변경은 서버에서 검증한다. 발주 전송·입고와 취소 작업은 발주 행을 잠가 동시 변경을 직렬화한다. 거래 이력은 조용히 삭제하거나 덮어쓰지 않고 취소·조정 이력을 남긴다.

## 권한 기본값

초기 계정은 Owner 1명과 Staff 1명이다. Owner는 매출·비용·매장 설정·발주 확정·수리비 입력을 포함한 운영 관리 권한을 갖는다. Staff는 허용된 재고 사용·폐기, 예약 착석, 시설 이상 등록을 수행할 수 있다. 수리 진행 상태 관리는 Owner 권한이다. Staff에게 매출·비용 정보, 역할 관리 및 발주 확정 권한을 주지 않는다. Manager는 향후 권한 확장을 위한 역할 값이며 기본 계정은 만들지 않는다.

## 검증 경계

실매장 사용 전에는 빈 DB 마이그레이션, 로그인과 역할별 차단, 매장 간 데이터 격리, 판매-재고 계산 및 중복 재시도, 예약 충돌, 백업 복원을 실제 환경에서 검증한다. 구현되지 않았거나 실행하지 않은 검증은 완료로 표현하지 않는다. 실제 POS 연동, 은행 대사, 유통기한 로트 추적, 전문 회계 기능은 별도 범위다.
